## 1. How the Planner Predicts the Future

Before executing a query, the cost-based optimizer must answer: *"If I filter by `status = 'pending'`, how many rows will match?"*

It does not scan the table to count rows. Instead, it queries statistical samples stored in **`pg_statistic`** (viewable through the user-friendly view **`pg_stats`**), generated by the `ANALYZE` command.

---

## 2. Inspecting `pg_stats`

You can inspect the exact mathematical distribution that PostgreSQL uses to make plan choices:

```sql
SELECT 
    tablename, 
    attname AS column_name, 
    null_frac, 
    n_distinct, 
    most_common_vals, 
    most_common_freqs 
FROM pg_stats 
WHERE tablename = 'users' AND attname = 'country';
```

### Key Metrics in `pg_stats`:
- **`null_frac`:** Percentage of rows where the column is NULL (e.g. `0.02` = 2%).
- **`n_distinct`:** If positive, the exact number of distinct values. If negative, the ratio of distinct values relative to total table rows (`-1.0` means unique).
- **`most_common_vals` (MCV):** The most frequently occurring values.
- **`most_common_freqs` (MCF):** The frequency distribution of those top values.
- **`histogram_bounds`:** Equal-frequency bucket dividers used to estimate range queries (`WHERE age BETWEEN 25 AND 35`).

---

## 3. Understanding MCVs and Histogram Bounds

When you run:
```sql
SELECT * FROM users WHERE country = 'US';
```
The optimizer checks `most_common_vals`. If `'US'` is present with frequency `0.45` in `most_common_freqs`, and `reltuples = 1,000,000`, the planner instantly estimates that **450,000 rows** will match—and immediately selects a `Seq Scan` instead of an index scan, knowing that jumping through an index 450,000 times would thrash disk I/O!

## 4. Tuning Statistics Targets for Skewed Data

By default, `ANALYZE` samples 100 histogram buckets (`default_statistics_target = 100`).

For heavily skewed, high-cardinality tables, you can increase the sampling depth for specific columns without slowing down global maintenance:

```sql
-- Increase statistics granularity for a high-cardinality column
ALTER TABLE transactions ALTER COLUMN merchant_id SET STATISTICS 1000;

-- Refresh statistics immediately
ANALYZE transactions (merchant_id);
```

## 5. The Multi-Column Correlation Blindspot

By default, PostgreSQL assumes that columns are **statistically independent**.

Consider a used car dealership table with columns `make` and `model`:
- $P(\text{make} = \text{'Audi'}) = 1\%$ (1 in 100 cars)
- $P(\text{model} = \text{'A4'}) = 0.5\%$ (1 in 200 cars)

If a query filters by `WHERE make = 'Audi' AND model = 'A4'`, the optimizer multiplies probabilities:
$$0.01 \times 0.005 = 0.00005 \text{ (1 in 20,000 rows!)}$$

**The Reality:** If a car is an `'A4'`, its make is **100% guaranteed** to be an `'Audi'`. The real probability is 1 in 200, not 1 in 20,000!
Because the optimizer assumes 1 row will match instead of 10,000, it makes terrible execution plan decisions (e.g. picking a slow Nested Loop join).

## 6. Multivariate Statistics with `CREATE STATISTICS`

PostgreSQL 10+ introduces **Extended Statistics** to track cross-column dependencies:

```sql
-- 1. Create extended multivariate statistics object
CREATE STATISTICS stat_cars_make_model 
ON make, model FROM cars;

-- 2. Compute statistics
ANALYZE cars;
```

### Types of Extended Statistics:
- **`ndistinct`:** Tracks real distinct count for combinations of columns.
- **`dependencies`:** Captures functional dependencies ($A \implies B$).
- **`mcv` (Postgres 12+):** Builds a multi-column Most Common Values list!

With `stat_cars_make_model` in place, the planner observes the correlated MCV list and produces **flawless row estimations**, restoring optimal query plans.

## 7. Hands-On Verification

```sql
CREATE TABLE test_correlation (
    state TEXT,
    zip_code TEXT
);

-- Populate heavily correlated zip codes and states
INSERT INTO test_correlation (state, zip_code)
SELECT 'NY', '10001' FROM generate_series(1, 100000);

ANALYZE test_correlation;

-- Check naive estimate
EXPLAIN SELECT * FROM test_correlation WHERE state = 'NY' AND zip_code = '10001';

-- Create extended statistics
CREATE STATISTICS stat_geo ON state, zip_code FROM test_correlation;
ANALYZE test_correlation;

-- Re-check estimate: Now matches actual row count perfectly!
EXPLAIN SELECT * FROM test_correlation WHERE state = 'NY' AND zip_code = '10001';
```

## 8. Summary & Key Takeaways

1. The query optimizer relies on `pg_stats` to estimate row counts and access costs.
2. `most_common_vals` and `histogram_bounds` guide index vs sequential scan selection.
3. Increase `SET STATISTICS` up to `1000` on critical skewed columns.
4. Independent column assumptions fail on correlated business data (e.g. city/zip, year/make/model).
5. Use `CREATE STATISTICS` to provide multivariate correlation telemetry to the optimizer.
