## 1. Why Output Values

You just ran `terraform apply` and it created a brand-new RDS database. Now your application
needs to know the database's connection endpoint to actually connect to it — but that endpoint
was generated by AWS *during* the apply; it didn't exist when you wrote your `.tf` files, and it's
buried somewhere inside Terraform's state file as one attribute among dozens on the
`aws_db_instance` resource. Are you supposed to `grep` through a JSON state file to find it? Or
worse, manually check the AWS console and copy-paste the hostname into your app's config by hand,
every single time you re-provision?

**Output values** are Terraform's answer: a declared, named "return value" for your configuration.
You tell Terraform "expose this specific attribute, under this name," and after every apply, that
value is printed to the console, retrievable via `terraform output`, and — critically — readable
by *other* Terraform configurations that need to consume it (like your app-deployment config
needing the database endpoint your infra config just created).

### Analogy

If a Terraform module is a factory, outputs are the loading dock — the one clearly labeled place
where finished products come out so trucks (other systems, other configs, human operators) know
exactly where to pick them up. Nobody should have to walk the factory floor (dig through state)
to find where the pallets are stacked.

### Under the Hood

```
┌─────────────────────────────────────────────────────────────┐
│                    terraform apply                            │
│                                                                 │
│  1. Resources created/updated (e.g. aws_db_instance.main)     │
│  2. AWS returns computed attributes (endpoint, ARN, id, ...)  │
│  3. Terraform writes ALL resource attributes into state       │
│                                                                 │
│         resource attributes live buried in .tfstate:          │
│         {"aws_db_instance.main": {"endpoint": "db.xyz...",     │
│           "arn": "arn:aws:rds:...", "id": "db-abc123", ...}}  │
└───────────────────────────┬───────────────────────────────────┘
                              │
                              │  `output` blocks declare which of
                              │  these values are worth naming and
                              │  surfacing
                              ▼
              ┌───────────────────────────────┐
              │   output "db_endpoint" {      │
              │     value = aws_db_instance.  │
              │              main.endpoint    │
              │   }                            │
              └───────────────┬───────────────┘
                              │
              ┌───────────────┼───────────────────┐
              ▼               ▼                   ▼
     terraform apply    terraform output     other Terraform configs
     console printout    (CLI / -json)        via terraform_remote_state
```

Outputs don't compute anything new — they just *name and expose* values that already exist
somewhere in the resource graph (resource attributes, variables, locals, module outputs), making
them consumable from outside the configuration that created them.

### Concrete Example

```hcl
# main.tf
resource "aws_db_instance" "main" {
  identifier     = "app-db"
  engine         = "postgres"
  instance_class = "db.t3.micro"
  username       = "app_admin"
  password       = var.db_password
  allocated_storage = 20
}

# outputs.tf
output "db_endpoint" {
  description = "Connection endpoint for the application database"
  value       = aws_db_instance.main.endpoint
}

output "db_port" {
  description = "Port the database listens on"
  value       = aws_db_instance.main.port
}
```

```bash
$ terraform apply
...
Apply complete! Resources: 1 added, 0 changed, 0 destroyed.

Outputs:

db_endpoint = "app-db.abcdef123456.us-east-1.rds.amazonaws.com:5432"
db_port = 5432
```

### Common Mistakes

- **Thinking outputs are only useful for humans reading the CLI.** Their bigger value is
  programmatic — CI/CD pipelines parsing `-json` output, or other Terraform configurations
  reading them via `terraform_remote_state` to wire infrastructure together across configs.
- **Not adding a `description`.** Just like variables, an undocumented output leaves the next
  engineer guessing what it's for and where its value comes from.
- **Outputting an entire resource instead of specific attributes.** `value =
  aws_db_instance.main` exposes every attribute (some potentially sensitive) instead of the
  one or two the consumer actually needs.

### Interview Answer

"Output values expose specific data from a Terraform configuration — resource attributes,
computed locals, or variables — as named values that can be viewed after an apply, retrieved
via `terraform output`, or consumed by other Terraform configurations through remote state. They
solve the problem of information that's only known after apply (like a generated ARN or DNS
endpoint) needing to flow to humans or other systems without manually digging through the state
file."

> **Memory hook:** Outputs are the factory's labeled loading dock — the one clear place finished goods come out, instead of trucks having to search the whole warehouse floor.

## 2. output Block Syntax

You've decided you want to expose the database endpoint. What exactly goes inside the `output`
block, and what optional knobs does it offer beyond just a bare value?

### Analogy

An `output` block is a shipping label on that loading-dock pallet: a name identifying what's
inside, a description of the contents, the actual value being shipped, and a "handle with care /
confidential" stamp when needed.

### Syntax Anatomy

```hcl
output "db_endpoint" {
  value       = aws_db_instance.main.endpoint      # required — the value to expose
  description = "Connection endpoint for the app database"   # recommended
  sensitive   = false                               # optional, default false
  depends_on  = [aws_db_instance.main]              # optional, rarely needed explicitly
}
```

| Argument | Required? | Purpose |
|----------|-----------|---------|
| `value` | Required | The expression to expose — a resource attribute, variable, local, or any valid expression |
| `description` | Optional but recommended | Documents what the output represents |
| `sensitive` | Optional (default `false`) | Redacts the value from CLI/plan output |
| `depends_on` | Optional, rarely needed | Forces an explicit dependency Terraform can't infer automatically |

### Under the Hood

Terraform automatically infers dependencies for an output from the expression in `value` — if
`value = aws_db_instance.main.endpoint`, Terraform already knows this output depends on
`aws_db_instance.main` and won't try to read it before that resource is created. `depends_on` on
an output is only needed in rare cases where the dependency is *not* visible in the expression
itself — for example, when a value depends on a side effect of another resource that isn't
directly referenced (a provisioner, or a resource whose creation must happen first for unrelated
reasons).

```hcl
resource "aws_instance" "web" {
  # ...
}

resource "aws_eip" "web" {
  instance = aws_instance.web.id
}

output "instance_public_ip" {
  description = "Public IP address of the web server"
  value       = aws_eip.web.public_ip   # dependency on aws_eip.web is inferred automatically
}
```

### Common Mistakes

- **Adding `depends_on` reflexively "to be safe."** In the vast majority of cases the reference
  inside `value` already establishes the correct dependency — adding `depends_on` unnecessarily
  adds noise and can occasionally create graph cycles in more complex configurations.
- **Naming outputs ambiguously across modules.** `output "id"` in five different child modules
  becomes confusing once you're wiring modules together — prefer specific names like
  `output "vpc_id"` or `output "db_instance_id"`.
- **Forgetting outputs are evaluated during `plan`, not just `apply`.** If the value references
  an attribute only known after creation (like an auto-generated ARN on a not-yet-existing
  resource), Terraform shows `(known after apply)` in the plan — this is expected, not an error.

### Interview Answer

"An `output` block requires a `value` expression and optionally takes `description` for
documentation and `sensitive` to redact it from output. Terraform automatically infers the
output's dependencies from whatever resources or data sources are referenced inside `value`, so
`depends_on` is rarely needed explicitly — only when a dependency isn't visible in the expression
itself."

> **Memory hook:** An output block is a shipping label — name, description, the actual value inside, and a confidential stamp when needed.

## 3. Sensitive Outputs

Your database module outputs the master password so the application-deployment config can wire
it straight into an app's environment variables without a human ever typing it manually. But by
default, that password would print in plaintext right there in the `terraform apply` console —
and in every CI log that ever runs that apply. Marking the output `sensitive = true` stops that
leak at the display layer.

### Analogy

A sensitive output is like a courier handing over a sealed envelope marked "confidential" — the
courier (Terraform) still delivers the contents to whoever's authorized to open it (another
config consuming the output, or a resource wired to it), but doesn't read its contents aloud in
the lobby (the console) on the way through.

### Syntax and Behavior

```hcl
output "db_password" {
  description = "Master password for the application database"
  value       = aws_db_instance.main.password
  sensitive   = true
}
```

```bash
$ terraform apply
...
Outputs:

db_password = <sensitive>
```

### Propagation Rule

If an output's `value` expression references *anything* already marked sensitive (a `sensitive =
true` variable, or another sensitive output), Terraform **requires** that output to also be marked
`sensitive = true` — it will error at plan time if you forget:

```
Error: Output refers to sensitive values

  To reduce the risk of accidentally exposing sensitive data in your
  configuration, Terraform requires that any root module output
  containing sensitive data be explicitly marked as sensitive to
  confirm your intent.
```

### Comparison — Sensitive Variable vs Sensitive Output

| | Sensitive Variable | Sensitive Output |
|---|---|---|
| **What it redacts** | The value when supplied as input (plan/apply console) | The value when exposed as a result (plan/apply console, `terraform output`) |
| **Forces sensitivity on...** | Anything computed from it (locals, outputs) | Nothing downstream — it's the "end of the line" for the config |
| **Still visible in state?** | Yes, plaintext in `.tfstate` | Yes, plaintext in `.tfstate` |
| **Still visible via `terraform output -json`?** | N/A (not an output) | Yes — `-json` still prints the real value; only human-readable CLI output redacts it |

### Common Mistakes

- **Assuming `terraform output -json` also hides sensitive outputs.** It does not — `-json` is
  meant for machine consumption and deliberately includes the real value (with a
  `"sensitive": true` flag alongside it) so automation can still use it. Anyone with access to run
  that command sees the real value.
- **Forgetting sensitive outputs still land in state in plaintext.** Just like sensitive
  variables, this is a CLI-display feature, not encryption — state file protection is still the
  real control.
- **Not marking a database password output as sensitive at all**, on the assumption "it's an
  internal config, nobody's watching the terminal" — CI logs are frequently retained, searchable,
  and readable by more people than expected.

### Interview Answer

"A `sensitive = true` output redacts its value from the human-readable `terraform plan`/`apply`
console output, showing `<sensitive>` instead. If the output's value is derived from an already-
sensitive variable or output, Terraform forces you to mark it sensitive too — it won't let
sensitivity silently leak through an unmarked output. That said, it's purely a display control:
the raw value is still stored in plaintext in the state file, and `terraform output -json` still
returns the real value for automation to consume."

> **Memory hook:** A sensitive output is a sealed envelope — delivered intact to whoever's authorized, just never read aloud in the lobby.

## 4. Outputs in terraform apply and -json

You've seen outputs print at the bottom of `terraform apply`. But how does a CI/CD pipeline
actually *consume* an output programmatically — parsing text meant for humans out of console
output? That's fragile and ugly. Terraform gives you a structured, script-friendly path instead.

### Analogy

The plain console printout of outputs is like a receipt taped to the outside of a shipped
package — readable by a person glancing at it. `-json` output is the same information as a
barcode/QR code on that same package — unreadable to a human at a glance, but instantly and
reliably parseable by a scanner (your CI script, `jq`, another program).

### Retrieving Outputs

```bash
# All outputs, human-readable
terraform output

# One specific output, human-readable
terraform output db_endpoint

# One specific output, raw value with no quotes (great for shell scripting)
terraform output -raw db_endpoint

# All outputs, machine-readable JSON
terraform output -json
```

Example `-json` output:

```json
{
  "db_endpoint": {
    "sensitive": false,
    "type": "string",
    "value": "app-db.abcdef123456.us-east-1.rds.amazonaws.com:5432"
  },
  "db_password": {
    "sensitive": true,
    "type": "string",
    "value": "actual-plaintext-password-here"
  }
}
```

Note: even a `sensitive` output shows its **real value** in `-json` — the `"sensitive": true`
field is metadata telling the consumer to *handle it carefully*, not a redaction.

### Consuming Outputs in a Script

```bash
#!/usr/bin/env bash
set -euo pipefail

terraform apply -auto-approve

DB_ENDPOINT=$(terraform output -raw db_endpoint)
echo "Deploying app with DB endpoint: ${DB_ENDPOINT}"

# Feed it into another tool, e.g. an app deployment step
aws ecs update-service \
  --cluster my-cluster \
  --service my-app \
  --force-new-deployment \
  --environment-overrides "DB_ENDPOINT=${DB_ENDPOINT}"
```

### terraform plan -json vs terraform output -json

| Command | What it shows |
|---------|----------------|
| `terraform output -json` | Only the **final output values** after the last apply — read from state |
| `terraform plan -json` | The **entire planned change set** (resources to add/change/destroy), of which planned output values are only one small part |

### Common Mistakes

- **Scraping `terraform apply`'s plain-text console output with regex in CI scripts.** It's
  fragile — formatting can change between Terraform versions. Always use `-json` or `-raw` for
  scripting.
- **Using `terraform output db_endpoint` (without `-raw`) in a shell variable assignment.**
  Without `-raw`, string outputs are wrapped in quotes in the text output, which then get
  embedded literally into your variable — `-raw` strips them for plain scalar values.
  `-raw` only works for outputs of type `string`; use `-json` for lists/maps/objects.
- **Assuming outputs are available before the first successful apply.** `terraform output` reads
  from the *current state* — if no apply has ever succeeded, there is no state and no output
  values to show.

### Interview Answer

"`terraform output` prints stored output values from the current state, either as formatted text
for humans, `-raw` for a single scalar value suitable for shell variables, or `-json` for
structured machine consumption — CI/CD pipelines typically pipe `-json` into `jq` or a scripting
language to extract values reliably rather than parsing human-oriented plain-text output. Even
sensitive outputs return their real value under `-json`, since it's intended for trusted
automation, not display."

> **Memory hook:** Plain output is the receipt taped to the box for a human to read; `-json` is the barcode a scanner reads reliably every time.

## 5. Using Outputs with Remote State

Your networking team's Terraform config creates a VPC and subnets. Your application team's
separate Terraform config needs to launch EC2 instances *into* that VPC. These are two entirely
different Terraform configurations, possibly in different repos, possibly owned by different
teams, run at different times. How does the app team's config get the VPC ID that only exists in
the networking team's state file? Outputs plus the `terraform_remote_state` data source are the
bridge.

### Analogy

Think of one team's Terraform state as a shipping manifest kept in a shared warehouse office.
Another team, needing to know "which container did the parts arrive in," doesn't re-run the
shipment — they walk into that office and read the specific line on the manifest they need
(the *output*) via a lookup window (`terraform_remote_state`).

### How It Works

```
┌──────────────────────────────┐          ┌──────────────────────────────┐
│   networking/ config          │          │   app/ config                 │
│                                │          │                                │
│  resource "aws_vpc" "main" {} │          │  data "terraform_remote_state"│
│                                │          │       "network" {              │
│  output "vpc_id" {            │          │    backend = "s3"              │
│    value = aws_vpc.main.id    │          │    config = {                  │
│  }                             │          │      bucket = "tf-state-co"    │
│                                │          │      key    = "network.tfstate"│
└──────────────┬─────────────────┘          │      region = "us-east-1"     │
               │                             │    }                           │
               │  terraform apply            │  }                             │
               ▼                             │                                │
      ┌────────────────────┐                │  resource "aws_instance" "app" │
      │  S3 remote backend  │◄───────read────┤    subnet_id = data.terraform_ │
      │  network.tfstate    │                │      remote_state.network.    │
      │  { outputs:          │                │      outputs.vpc_id            │
      │    vpc_id = "vpc-.." │                │  }                             │
      │  }                   │                └──────────────────────────────┘
      └────────────────────┘
```

### Concrete Example

```hcl
# networking/outputs.tf
output "vpc_id" {
  description = "ID of the shared VPC"
  value       = aws_vpc.main.id
}

output "private_subnet_ids" {
  description = "IDs of the private subnets"
  value       = aws_subnet.private[*].id
}
```

```hcl
# app/main.tf
data "terraform_remote_state" "network" {
  backend = "s3"
  config = {
    bucket = "acme-terraform-state"
    key    = "networking/terraform.tfstate"
    region = "us-east-1"
  }
}

resource "aws_instance" "app" {
  ami           = "ami-0c101f26f147fa7fd"
  instance_type = "t3.micro"
  subnet_id     = data.terraform_remote_state.network.outputs.private_subnet_ids[0]

  tags = {
    Name = "app-server"
    VPC  = data.terraform_remote_state.network.outputs.vpc_id
  }
}
```

Note: `data.terraform_remote_state.network.outputs` is a map of *every* output the networking
config declared — only values explicitly exposed via `output` blocks in that other config are
reachable this way. If the networking config never output `vpc_id`, the app config simply cannot
see it, no matter how it's defined internally.

> This is a preview. Remote state backends (S3 + DynamoDB locking, Terraform Cloud state, state
> locking mechanics, and workspace-scoped state) are covered in full in Phase 4 (State Management)
> and Phase 9 (Terraform Cloud & Remote Backends).

### Common Mistakes

- **Forgetting `terraform_remote_state` is read-only.** It can consume another config's outputs,
  but cannot modify that state — if the app config needs the networking team to expose a new
  value, someone has to add an `output` block to the *networking* config and re-apply it first.
- **Tight-coupling too many configs to each other's remote state.** A long chain of configs each
  depending on another's state via `terraform_remote_state` can turn a single upstream change
  into a fragile, hard-to-reason-about apply order across many teams — this is one reason larger
  organizations often prefer well-defined modules (Phase 6) or a service registry over deep
  remote-state chaining.
- **Not realizing a stale remote state read is possible.** `terraform_remote_state` reads
  whatever is in the *state file* at the moment you run `plan`/`apply` — if the networking config
  changed but hasn't been applied yet, the app config sees the *last applied* values, not
  in-flight ones.

### Interview Answer

"`terraform_remote_state` is a data source that lets one Terraform configuration read another
configuration's declared output values by pointing at its state backend. Only values the source
configuration explicitly exposed via `output` blocks are visible this way — it's read-only, and
it reads whatever was last successfully applied, not any in-progress changes. It's the standard
mechanism for wiring together configurations owned by different teams or split across repos,
such as an app team consuming a VPC ID from a networking team's state."

> **Memory hook:** `terraform_remote_state` is walking into another team's warehouse office and reading one labeled line off their shipping manifest — you can look, you can't rewrite it, and you only see the manifest's last finalized version.

## 6. Common Mistakes

A roundup of the output-specific mistakes that show up repeatedly in real configurations —
worth reading as a standalone checklist even if you caught some of these in earlier sections.

### Referencing an Output Before Any Apply Has Run

```bash
$ terraform output db_endpoint
╷
│ Warning: No outputs found
```

Outputs are read from *state*. If `terraform apply` has never succeeded, there is no state, and
therefore no output values exist yet — this is not a bug, it's the expected behavior for a
brand-new configuration.

### Wrong or Missing Dependency Chains

```hcl
# BAD — output references a resource attribute that Terraform can compute
# before the resource that actually matters has finished
output "app_url" {
  value = "https://${aws_instance.app.public_dns}"
}
# If aws_instance.app isn't actually done configuring (e.g., a provisioner
# still running inside it), this output can be technically "known" but
# functionally not yet usable.
```

```hcl
# BETTER — depend on the thing that signals true readiness
resource "null_resource" "wait_for_app" {
  depends_on = [aws_instance.app]
  provisioner "local-exec" {
    command = "until curl -sf https://${aws_instance.app.public_dns}/health; do sleep 5; done"
  }
}

output "app_url" {
  value      = "https://${aws_instance.app.public_dns}"
  depends_on = [null_resource.wait_for_app]
}
```

This pattern is advanced (provisioners are covered fully in Phase 8) — the point here is that
Terraform's dependency graph guarantees *creation order*, not *application-level readiness*, and
an output can technically resolve before the underlying service is actually ready to be used.

### Comparison Table — Output Pitfalls at a Glance

| Mistake | Symptom | Fix |
|---------|---------|-----|
| Reading output before first apply | `No outputs found` warning | Run `terraform apply` at least once first |
| Exposing a whole resource instead of an attribute | Overexposed data, harder to consume | `value = aws_instance.web.public_ip`, not `value = aws_instance.web` |
| Forgetting `sensitive = true` propagation | Plan fails with "Output refers to sensitive values" | Mark the output `sensitive = true` |
| Scraping plain-text CLI output in scripts | Brittle parsing, breaks across TF versions | Use `-json` or `-raw` |
| Assuming remote state is "live" | Stale values after upstream changes not yet applied | Re-run `terraform apply` in the source config first |

> **Memory hook:** An output is only as fresh, complete, and safe as the state it's read from — no state yet, no output; wrong exposure, overexposed data; stale upstream apply, stale downstream value.

## 8. Interview Q&A

---

**Q1: What is the purpose of an `output` block in Terraform?**

A: An `output` block exposes a specific value from a Terraform configuration — usually a resource
attribute only known after apply, like a generated ARN or endpoint — so it can be viewed via the
CLI, retrieved with `terraform output`, or consumed by other Terraform configurations through
`terraform_remote_state`.

---

**Q2: How does Terraform know the dependency order for an output?**

A: It's inferred automatically from the expression in the output's `value` argument — if the
value references `aws_instance.web.public_ip`, Terraform already knows the output depends on
`aws_instance.web`. `depends_on` on an output is only needed when a dependency exists but isn't
visible in the expression itself.

---

**Q3: What does `sensitive = true` do on an output, and what doesn't it do?**

A: It redacts the value from human-readable `terraform plan`/`apply` console output, printing
`<sensitive>` instead, and it forces propagation — any output derived from an already-sensitive
value must also be marked sensitive. It does not encrypt the value in the state file (still
plaintext there) and does not hide it from `terraform output -json`, which always shows the real
value for automation.

---

**Q4: How do you consume a Terraform output value in a CI/CD script reliably?**

A: Use `terraform output -raw <name>` for a single scalar string value (no surrounding quotes,
safe to assign directly to a shell variable), or `terraform output -json` for structured/complex
values (lists, maps, objects), parsed with a tool like `jq`. Avoid scraping the plain-text console
output, since its formatting can change between Terraform versions.

---

**Q5: What is `terraform_remote_state` and what problem does it solve?**

A: It's a data source that reads another Terraform configuration's declared output values
directly from that configuration's state backend. It solves the problem of sharing data — like a
VPC ID or subnet list — between separate configurations (often owned by different teams) without
manually copying values or re-running the upstream config.

---

**Q6: Can `terraform_remote_state` modify the state it reads?**

A: No — it is strictly read-only. It can only surface values that the source configuration
already exposed via its own `output` blocks; if a value wasn't declared as an output there, it's
not visible through remote state at all, and consuming configs cannot add new outputs to it
themselves.

---

**Q7: Why does `terraform output` sometimes report "No outputs found" on a fresh clone of a
repo?**

A: Because output values are read from the *state file*, and a freshly cloned repo (or a config
that has never had `terraform apply` run successfully) has no state yet. The fix is simply to run
`terraform apply` at least once — outputs are populated as part of a successful apply.

---

**Q8: What's a common mistake when outputting resource data?**

A: Outputting an entire resource object (`value = aws_instance.web`) instead of the one or two
specific attributes a consumer actually needs (`value = aws_instance.web.public_ip`). This
overexposes data — including potentially sensitive fields — and makes the output harder for
downstream configs to consume predictably.

---

**Q9: Does an output being "known after apply" during `terraform plan` guarantee the underlying
resource is fully functional?**

A: No — Terraform's dependency graph guarantees creation *order*, not application-level
*readiness*. A value like a public DNS name can resolve as soon as the resource attribute exists,
even if a service running inside that resource (e.g., configured by a provisioner) isn't actually
ready to serve traffic yet. Readiness checks require explicit patterns like health-check
provisioners or external orchestration.

---

**Q10: If two Terraform configs each need a value the other produces, is remote state chaining
always the right solution?**

A: Not necessarily. For a small number of clearly-owned boundaries (e.g., networking team → app
team), `terraform_remote_state` works well. But long chains of configs depending on each other's
remote state can create fragile, hard-to-reason-about apply ordering across teams — at larger
scale, well-designed shared modules (Phase 6) or an external service registry/parameter store are
often preferred over deep remote-state coupling.
