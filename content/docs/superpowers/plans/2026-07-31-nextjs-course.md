- `02-Project-Structure-and-Conventions.md`: **Problem** — without a convention, every team invents its own routing/config setup, making it hard to jump between codebases. **Analogy** — the `app/` directory conventions are like a apartment building's standardized floor plan — every unit (route) has the same named rooms (`page.js`, `layout.js`) in the same place, so you always know where to look. **Definition** — the App Router's file-based convention: `app/` holds routes, `public/` holds static assets, `next.config.js` holds build config, special filenames (`page.js`, `layout.js`, etc., previewed here, detailed in Phase 2) trigger specific framework behavior just by existing at a path. **Internal working** — a directory-tree diagram showing `app/page.js` → `/`, `app/about/page.js` → `/about`, `app/blog/[slug]/page.js` → `/blog/:slug`, annotated with which file maps to which URL. **Example** — a real project tree in a fenced code block plus the exact minimal contents of a `page.js` (`export default function Page() { return <h1>Hello</h1> }`). **Compare** — table: `app/` (App Router, Server Components by default) vs. legacy `pages/` (Pages Router, Client Components by default, file = route directly) — explicitly note this course only covers `app/` per the spec's scope decision, and this table exists purely so readers recognize legacy code if they encounter it. **Common mistakes** — putting a route file directly in `app/` without a folder (e.g. `app/about.js` instead of `app/about/page.js` — the App Router requires the special filename inside a folder, not a bare file); forgetting `public/` assets are referenced from the URL root (`/logo.png`, not `/public/logo.png`). **Interview answer** — paragraph on the App Router's file-based routing convention and why it replaces manual route configuration. **Memory hook** — "The folder IS the URL; the filename IS the behavior."
- `03-React-Server-Components-Mental-Model.md`: **Problem** — shipping a fully client-rendered React app means every component's JS (and its dependencies) goes to the browser even if that component never needs interactivity, bloating the bundle. **Analogy** — Server Components are like a restaurant kitchen (work happens behind the scenes, only the finished plate — HTML — is sent to the table); Client Components are like an open-counter station where the customer (browser) can interact directly (add hooks, click handlers). **Definition** — React Server Components (RSC) render entirely on the server and send only HTML (plus a compact serialized description) to the browser — no JS for that component ships; Client Components (marked `"use client"`) render on the server for the initial HTML too, but their JS DOES ship so they can hydrate and become interactive. **Internal working** — diagram: `Server Component tree → rendered to RSC payload → sent to browser → Client Components hydrate within that HTML`, noting Server Components are the DEFAULT in `app/` with no directive needed. **Example** — a component with no `"use client"` (Server Component, e.g. reading from a database or file directly) next to one with `"use client"` (e.g. a counter using `useState`). **Compare** — table: Server Component vs. Client Component — can use hooks (no/yes), can access backend directly (yes/no), ships JS to browser (no/yes), can use browser APIs (no/yes). **Common mistakes** — adding `"use client"` to everything "just in case," defeating the whole benefit of RSC; trying to use `useState`/`useEffect` in a file without `"use client"` and hitting a build error. **Interview answer** — paragraph explaining RSC's value prop (less JS shipped, direct backend access) and the mental model of "Server Components by default, Client Components opt-in." **Memory hook** — "No `use client` = stays in the kitchen. `use client` = comes out to the counter and can talk back."

Content requirements (build on Phase 1 Lesson 2's directory-convention preview rather than re-teaching it):

- `01-Special-Files-and-Layouts.md`: **Problem** — every page in a site typically shares a header/nav/footer; re-importing and wrapping that markup in every single `page.js` is repetitive and error-prone (miss one page, get an inconsistent header). **Analogy** — a `layout.js` is like a picture frame around a rotating art exhibit — the frame (nav/footer) stays fixed while the art (`page.js` content, passed as `children`) changes underneath. **Definition** — special filenames inside an `app/` route folder trigger specific behavior: `page.js` (the route's actual UI), `layout.js` (shared UI wrapping the page AND all nested routes, persists across navigation without re-rendering), `template.js` (like layout but re-mounts on navigation), `loading.js` (auto-wraps the segment in `<Suspense>`, shown while data loads), `error.js` (a Client Component error boundary for that segment). **Internal working** — diagram nested layouts: `app/layout.js` (root, required, wraps `<html>`/`<body>`) → `app/dashboard/layout.js` (wraps only `/dashboard/*`) → `app/dashboard/page.js`, showing how layouts nest and only the innermost `page.js` changes on navigation between sibling routes. **Example** — a root `app/layout.js` with `<html><body>{children}</body></html>` plus a nested `app/dashboard/layout.js` adding a sidebar. **Compare** — table: `layout.js` vs. `template.js` vs. `page.js` — persists state across navigation (yes/no/n-a), required at root (yes/no/no), receives `children` (yes/yes/no). **Common mistakes** — forgetting the root `app/layout.js` must contain `<html>` and `<body>` tags (Next.js won't inject them for you at the root); putting page-specific logic in a shared `layout.js` and being surprised it doesn't re-run when navigating between sibling pages (that's the intended behavior — use `template.js` if you need remounting). **Interview answer** — paragraph on how nested layouts compose and why they avoid the "wrap every page manually" problem. **Memory hook** — "Layout is the picture frame that stays; Page is the art that swaps."
- `02-Dynamic-Segments-and-Route-Groups.md`: **Problem** — you can't hand-write a folder for every possible blog slug or product ID; you need one folder that matches many URLs and gives you the actual value that was requested. **Analogy** — a dynamic segment (`[id]`) is like a hotel room number sign that says "Room ___" — one physical sign template, filled in differently for each guest; a route group `(marketing)` is like a filing folder used only to organize your own drawers — the label never appears on the mail addressed to the recipient. **Definition** — `[slug]` matches a single dynamic path segment (value available via the page's `params`), `[...slug]` (catch-all) matches one-or-more remaining segments as an array, `[[...slug]]` (optional catch-all) also matches the base route with zero segments, `(groupName)` organizes routes/applies a layout to a subset WITHOUT adding a URL segment. **Internal working** — table mapping folder → matched URL → `params` shape for all four patterns (`[id]`, `[...slug]`, `[[...slug]]`, `(group)`). **Example** — `app/blog/[slug]/page.js` reading `params.slug`; `app/shop/[...categories]/page.js` reading `params.categories` as an array. **Compare** — table: `[slug]` vs. `[...slug]` vs. `[[...slug]]` — matches base route with no segment (no/no/yes), segments matched (exactly 1/1+/0+), `params` type (string/array/array-or-undefined). **Common mistakes** — expecting `[...slug]` to match zero segments too (it requires at least one — use `[[...slug]]` for the optional/zero-or-more case); putting a route group's parentheses in the actual URL mentally (e.g. thinking `(marketing)/about` serves at `/marketing/about` — it serves at `/about`, the group name is invisible in the URL). **Interview answer** — paragraph distinguishing dynamic segments from route groups and when to reach for each. **Memory hook** — "Square brackets `[ ]` capture a value into the URL; round brackets `( )` organize files WITHOUT touching the URL."
- `03-Parallel-and-Intercepting-Routes.md`: **Problem** — some UIs need to show two independently-navigable sections at once in the same layout (e.g. a dashboard's main feed AND a notifications panel, each with its own loading/error state), or need a route to render differently when reached via in-app navigation (e.g. a photo opened as a modal from a feed) vs. a direct URL visit (the same photo as a full page). **Analogy** — parallel routes (`@slot`) are like a TV with picture-in-picture — two independent "channels" (route slots) rendering simultaneously inside one screen (layout); an intercepting route (`(.)folder`) is like a pop-up preview window that appears when you click a link from within the app, versus the full page you'd get by typing that URL directly into a fresh tab. **Definition** — `@slotName` folders define parallel route slots rendered as named props into their shared `layout.js`; `(.)`/`(..)`/`(...)` prefixed folders intercept a route so navigating to it FROM a specific origin within the app renders the intercepted (often modal) version instead of the full page. **Internal working** — diagram a dashboard `layout.js` receiving both `children` (default slot) and `@analytics` (named slot) as props simultaneously; diagram a photo-feed intercepting route where clicking a thumbnail (soft navigation) shows a modal via `(.)photo/[id]`, but a hard refresh on that same URL renders the full `photo/[id]/page.js` instead. **Example** — `app/@analytics/page.js` alongside `app/layout.js` receiving `{ children, analytics }` props. **Compare** — table: parallel routes vs. intercepting routes — solves (independent simultaneous sections / different UI for soft-nav vs. direct visit), URL segment added (yes, via slot convention but not visible.../no extra segment), typically paired together (yes, intercepting + parallel routes are commonly combined for modals). **Common mistakes** — forgetting a parallel route slot needs its OWN `default.js` for the case where no route currently matches that slot (otherwise Next.js has no fallback and can 404 within that slot on some navigations); assuming an intercepting route replaces the full page entirely rather than layering (a direct visit/refresh to the intercepted URL still needs its own full `page.js` to render standalone). **Interview answer** — paragraph explaining the modal-photo-feed pattern as the canonical example combining both features. **Memory hook** — "Parallel routes render side-by-side; intercepting routes render differently depending on HOW you arrived."

Content requirements (deepen Phase 1 Lesson 3's RSC preview rather than re-teach the basic definition):

- `01-The-RSC-Client-Boundary.md`: **Problem** — once you mark one component `"use client"`, developers often assume everything it imports becomes client-side too, or conversely try to use server-only APIs (like a database client) inside it, hitting confusing build errors. **Analogy** — `"use client"` is a border checkpoint on a map: once you cross it, everything downstream (every component YOU import from inside a Client Component) is also on the client side of the border, even without its own directive. **Definition** — `"use client"` at the top of a file marks that module (and everything imported by it) as part of the client bundle; the directive is NOT inherited upward (a Server Component can still import and render a Client Component) but IS inherited downward through that Client Component's own imports. **Internal working** — diagram a component tree: `ServerComponent → ClientComponent ("use client") → ChildA (no directive, but still bundled client-side because its parent is a Client Component)`, contrasted with `ServerComponent → ChildB (no directive, stays server-side)`. **Example** — a `Page.js` (Server Component, no directive) importing a `Counter.js` (`"use client"`, uses `useState`). **Compare** — table: crossing the boundary top-down (Server importing Client: allowed, common) vs. bottom-up (Client importing Server directly: NOT allowed as a direct render — must use the children-passing pattern from Lesson 2). **Common mistakes** — putting `"use client"` on a top-level layout "to be safe," pushing the entire app into client-side rendering; trying to `import` and directly render a Server Component's function from inside a Client Component (not supported — only passing it as `children`/props from a Server Component parent works, detailed in Lesson 2). **Interview answer** — paragraph on how the client boundary propagates and why it's a common source of "why is my bundle so big" bugs. **Memory hook** — "`use client` is a one-way door: once you're through it, so is everything you personally `import` next."
- `02-Composition-Patterns.md`: **Problem** — a Client Component (e.g. a tabs widget needing `useState`) often needs to render Server Component content INSIDE it (e.g. a data-heavy panel per tab) — but Lesson 1 established Client Components can't directly import/render Server Components. **Analogy** — passing a Server Component as `children` into a Client Component is like handing a sealed, already-cooked meal (rendered HTML) through a serving window into the dining room (client side) — the client-side component just places it on the table without needing to know how it was cooked. **Definition** — the "children as slot" pattern: a Server Component parent renders the Client Component and passes Server Component output as `children` (or another prop); the Client Component never imports the Server Component itself, it just receives already-rendered content as a prop and drops it into its JSX. **Internal working** — code-flow diagram: `Page.js (Server) renders <Tabs>{<ServerHeavyPanel/>}</Tabs>` → `Tabs.js ("use client")` receives `children` prop and just renders `{children}` inside its interactive tab-switching markup — the heavy panel was rendered server-side BEFORE being handed to the client component. **Example** — the actual `Tabs.js` accepting `{ children }` and a `Page.js` composing it with a Server Component. **Compare** — table: "import and render directly" (works Server→Client, fails Client→Server) vs. "pass as children/props" (works in both directions, the recommended pattern). **Common mistakes** — trying to `import ServerHeavyPanel from './ServerHeavyPanel'` inside `Tabs.js` and rendering it directly (fails/defeats the purpose — pulls it into the client bundle or errors depending on what it does); over-using this pattern for trivial cases where the component could just stay a Server Component with no interactivity needed at all. **Interview answer** — paragraph explaining the children-slot composition pattern as the standard way to keep Client Components "thin" (interactivity shell only) while Server Components do the data-heavy rendering. **Memory hook** — "Don't import the chef into the dining room — hand the plate through the window instead (pass as children)."
- `03-Serialization-and-Boundary-Rules.md`: **Problem** — passing data as props from a Server Component to a Client Component isn't like a normal in-memory function call — the data has to physically travel from server to browser, so not everything can cross. **Analogy** — the Server→Client prop boundary is like mailing a package internationally: only physical, describable objects (plain data) can go in the box; you can't mail a live phone call (a function) or a person standing in your office (a class instance/DOM node). **Definition** — props passed from a Server Component to a Client Component must be serializable (plain objects, arrays, strings, numbers, booleans, dates-as-strings) — functions, class instances, and Symbols cannot cross (with the notable exception of Server Actions, a special function type covered in Phase 6, which DO cross via a different mechanism). **Internal working** — diagram the RSC payload serialization step: `Server Component props → serialized into the RSC wire format → sent over the network → deserialized on the client → passed into the Client Component`. **Example** — a valid case (`<ClientWidget data={{ id: 1, name: "Alice" }} />`) vs. an invalid case (`<ClientWidget onSave={function(){...}} />` passed from a Server Component — the fix, moving `onSave`'s logic into a Server Action or into the Client Component itself). **Compare** — table: what crosses the boundary — plain objects/arrays (yes), Dates (only as ISO strings, not Date instances, unless using a library that handles this), functions (no, except Server Actions), class instances/Maps/Sets (no, not natively serializable). **Common mistakes** — trying to pass an event handler function as a prop from a Server Component down to a Client Component (build/runtime error — event handlers must be defined IN a Client Component, not passed into one from a Server Component); passing a `Date` object directly and being surprised by serialization quirks (safer to pass an ISO string and construct the `Date` client-side if needed). **Interview answer** — paragraph on the serialization boundary and why it's a deliberate constraint, not a bug. **Memory hook** — "If you can't put it in a JSON envelope, it can't cross from server to client."
