# Spring Boot Interview Q&A

50 questions covering the full Spring Boot course, organized by topic. Answers go deeper than a typical cheatsheet — Spring's proxy-based magic hides a lot of subtlety, and several questions specifically target the "gotchas" that trip up even experienced developers in interviews and in production.

---

## Core Spring: IoC, DI & Beans (Q1-Q10)

**Q1. What is Inversion of Control and how does Spring implement it?**
Answer: Inversion of Control is a design principle where an object's dependencies are provided by an external entity rather than the object creating or looking them up itself, inverting the traditional flow of control where the object is in charge. Spring implements IoC through its `ApplicationContext`, which acts as a container that instantiates, configures, and wires together objects — called beans — based on configuration metadata (annotations, XML, or Java `@Configuration` classes). Instead of a class calling `new PaymentGateway()` internally, Spring constructs the `PaymentGateway` bean once and injects it wherever it's needed. This decouples classes from the concrete construction logic of their collaborators, which is what makes unit testing, swapping implementations, and layering an application dramatically easier.

---

**Q2. What is Dependency Injection and what are its three forms in Spring?**
Answer: Dependency Injection (DI) is the specific mechanism Spring uses to achieve IoC: instead of a component looking up or constructing its dependencies, they are "injected" into it by the container. The three forms are constructor injection (dependencies passed via the constructor), setter injection (dependencies set via public setter methods after construction), and field injection (dependencies injected directly into private fields via reflection, typically with `@Autowired` on the field). Constructor injection is the strongly recommended default because it makes dependencies explicit and final, allows the object to be fully valid immediately after construction, works naturally with unit testing without needing a Spring context, and fails fast at startup if a circular dependency exists rather than silently working around it.

---

**Q3. What is the Spring ApplicationContext and how does it differ from a BeanFactory?**
Answer: `BeanFactory` is the root interface providing the most basic IoC container capabilities — bean instantiation, wiring, and lifecycle management — using lazy initialization by default. `ApplicationContext` extends `BeanFactory` and adds enterprise features: eager singleton instantiation at startup (surfacing configuration errors immediately rather than at first use), event publication (`ApplicationEventPublisher`), internationalization support (`MessageSource`), AOP integration, and automatic registration of `BeanPostProcessor`/`BeanFactoryPostProcessor` beans. In practice, virtually all Spring Boot applications use an `ApplicationContext` implementation (such as `AnnotationConfigServletWebServerApplicationContext`); `BeanFactory` is rarely used directly except in extremely resource-constrained scenarios.

---

**Q4. Explain the Spring bean lifecycle in detail.**
Answer: The container first instantiates the bean by calling its constructor (with constructor-injected dependencies resolved first). Next it populates properties via setter or field injection. Then, if the bean implements aware interfaces (`BeanNameAware`, `ApplicationContextAware`), those callbacks fire. `BeanPostProcessor.postProcessBeforeInitialization` runs next, followed by any `@PostConstruct`-annotated method or `InitializingBean.afterPropertiesSet()`, then `postProcessAfterInitialization` — this is the exact point where AOP proxies (for `@Transactional`, `@Cacheable`, `@Async`) get created, wrapping the raw bean. The bean is then ready for use for the remainder of the application's life. On container shutdown, singleton beans receive a `@PreDestroy` callback or `DisposableBean.destroy()` call, in that order, giving them a chance to release resources like connection pools or file handles.

---

**Q5. What causes a circular dependency error in Spring and how do you resolve one?**
Answer: A circular dependency occurs when bean A requires bean B during construction and bean B requires bean A, so neither can be fully constructed first — with pure constructor injection, Spring cannot resolve the cycle and throws `BeanCurrentlyInCreationException` at startup. Spring can partially work around this for singleton beans using setter or field injection, because it can register an early, not-yet-fully-initialized reference of one bean before it finishes populating the other's dependencies, but this "early reference" trick doesn't work for constructor injection and is generally considered a design smell rather than something to rely on. The right fix is almost always to refactor: extract the shared behavior into a third bean that both A and B depend on, use `@Lazy` on one of the injection points to defer resolution until first use, or restructure the responsibilities so the cycle doesn't exist in the first place. Relying on field injection specifically to dodge this error just hides an underlying design problem rather than solving it.

---

**Q6. What is the difference between @Component, @Service, @Repository, and @Controller?**
Answer: All four are meta-annotations built on top of `@Component`, so structurally they behave identically as far as component scanning and bean registration are concerned — each causes Spring to detect the class during `@ComponentScan` and register it as a bean. The distinction is purely semantic and enables extra framework behavior layered on top: `@Repository` triggers Spring's persistence exception translation, converting JDBC/JPA-provider-specific exceptions into Spring's unified `DataAccessException` hierarchy via a registered `PersistenceExceptionTranslationPostProcessor`. `@Controller` marks a class for Spring MVC's request-mapping machinery, and `@Service` carries no extra framework behavior at all — it exists purely to communicate intent to other developers that the class holds business logic. Using the correct stereotype improves readability and, in `@Repository`'s case, unlocks real functional behavior, so it isn't purely cosmetic.

---

**Q7. What is a circular dependency between @Configuration classes and how does @Lazy help?**
Answer: When two `@Configuration` classes each define `@Bean` methods that reference beans from the other configuration class, Spring must resolve both classes during context startup, which can create the same kind of unresolved cycle seen between regular beans, particularly with constructor-based bean methods. Annotating one of the conflicting `@Bean` methods, or the injection point that consumes it, with `@Lazy` tells Spring to inject a proxy instead of resolving the real bean immediately — the proxy defers actual bean creation until the first method call on it, breaking the cycle at startup time. This is a legitimate escape hatch for framework-level or third-party integration beans where refactoring isn't practical, but for application code it usually signals that a configuration class is taking on too many unrelated responsibilities and should be split.

---

**Q8. What is the difference between @Primary and @Qualifier, and when would you use each?**
Answer: Both resolve ambiguity when multiple beans of the same type exist and Spring can't determine which one to autowire by type alone. `@Primary` is applied at the bean definition site and establishes a default candidate that wins whenever a matching type is requested without further qualification — it's a "soft default" for the common case. `@Qualifier("beanName")` is applied at the injection point and explicitly names which bean to inject, overriding `@Primary` if both are present for that particular injection point. In practice, `@Primary` is used when one implementation is genuinely the sensible default across the whole app (e.g., a production `Clock` bean), while `@Qualifier` is used when different call sites genuinely need different specific implementations, such as multiple `RestTemplate` beans configured for different downstream services.

---

**Q9. What is the difference between singleton and prototype bean scope, and what's a common mistake developers make with prototype beans?**
Answer: A singleton-scoped bean (Spring's default) has exactly one shared instance per `ApplicationContext`, created eagerly at startup and reused for every injection point. A prototype-scoped bean gets a brand-new instance every time it's requested from the container. The common mistake is injecting a prototype bean directly as a field into a singleton bean — because the singleton is only constructed once, the prototype dependency is resolved only once at that point and then reused forever, defeating the purpose of prototype scope entirely. The correct pattern is to inject an `ObjectProvider<PrototypeBean>` or `ObjectFactory<PrototypeBean>` into the singleton and call `.getObject()` each time a fresh prototype instance is actually needed, or use method injection via `@Lookup`.

---

**Q10. What are BeanPostProcessor and BeanFactoryPostProcessor, and why do they matter for understanding Spring's "magic"?**
Answer: A `BeanFactoryPostProcessor` runs once, very early, and operates on bean *definitions* (metadata) before any bean is actually instantiated — it can add, modify, or remove bean definitions, which is how mechanisms like `@ConfigurationProperties` binding and property placeholder resolution (`${...}`) hook into the container. A `BeanPostProcessor` runs per-bean, after instantiation, wrapping around the `@PostConstruct`/`InitializingBean` initialization callbacks — this is precisely the extension point Spring AOP uses to wrap beans in dynamic proxies for `@Transactional`, `@Cacheable`, `@Async`, and `@Autowired` field/method injection itself is implemented via an `AutowiredAnnotationBeanPostProcessor`. Understanding these two extension points demystifies most of what looks like "magic" in Spring — annotations don't do anything on their own, they're metadata that specific post-processors scan for and act on during context startup.

## Spring Boot Fundamentals & REST APIs (Q11-Q20)

**Q11. What does @SpringBootApplication actually do, and what three annotations does it combine?**
Answer: `@SpringBootApplication` is a convenience meta-annotation combining `@Configuration` (marks the class as a source of bean definitions), `@EnableAutoConfiguration` (triggers Spring Boot's conditional auto-configuration mechanism that inspects the classpath and configures beans like a `DataSource` or `DispatcherServlet` automatically), and `@ComponentScan` (scans the current package and sub-packages for `@Component`-annotated classes to register as beans). Because `@ComponentScan` defaults to scanning from the annotated class's package downward, the conventional advice to place the main application class in the root package of the project isn't just a style preference — it directly determines what gets auto-detected. Each of the three constituent annotations can be applied individually with custom parameters if the defaults don't fit, which is common in modular multi-package projects.

---

**Q12. How does Spring Boot auto-configuration actually decide what to configure?**
Answer: Auto-configuration works through classes annotated with `@AutoConfiguration` (or the older `@Configuration` for pre-3.x) listed in `META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports`, each guarded by conditional annotations like `@ConditionalOnClass`, `@ConditionalOnMissingBean`, and `@ConditionalOnProperty`. At startup, Spring Boot evaluates each candidate configuration's conditions against the current classpath, existing bean definitions, and active properties, and only applies configurations whose conditions all pass — for example, `DataSourceAutoConfiguration` only activates if a JDBC driver and `DataSource` class are on the classpath and no other bean already defines a `DataSource`. This "opinionated but overridable" design means adding a starter dependency is often enough to get a fully working subsystem, while defining your own bean of the same type silently disables the corresponding auto-configuration through `@ConditionalOnMissingBean`.

---

**Q13. What is the difference between application.properties and application.yml, and how do Spring profiles interact with them?**
Answer: Both formats configure the exact same underlying property keys and are functionally equivalent — YAML simply expresses nested keys hierarchically (`spring.datasource.url`) rather than as flat dotted strings, which reduces repetition for deeply nested configuration and is generally preferred for readability in larger projects. Spring profiles let you activate different sets of properties for different environments; in a single YAML file this is done with `---` document separators and `spring.config.activate.on-profile: dev`, while in properties files it typically means separate files like `application-dev.properties` and `application-prod.properties`. The active profile is set via `spring.profiles.active` (as a command-line arg, environment variable, or system property), and Spring Boot merges the profile-specific properties on top of the base `application.properties`/`.yml`, with profile-specific values winning on conflict.

---

**Q14. What is the Spring Boot property resolution order, from lowest to highest precedence?**
Answer: Spring Boot resolves the same property from many possible sources, applying a strict precedence order so the most specific/operational source always wins: defaults in code, then `application.properties`/`.yml` packaged in the jar, then profile-specific variants of those files, then config data outside the packaged jar (e.g., in the same directory as the jar or `/config` subdirectory), then OS environment variables, then Java system properties (`-D` flags), and finally command-line arguments passed to `SpringApplication.run`, which have the highest precedence of all. This ordering is precisely why production deployments typically override configuration via environment variables or command-line flags rather than editing the packaged properties file — it lets the same artifact be promoted through environments without rebuilding.

---

**Q15. What is the difference between @RequestParam, @PathVariable, and @RequestBody?**
Answer: `@PathVariable` extracts a value from a templated segment of the URI path itself, such as the `{id}` in `/orders/{id}`, and is used for identifying a specific resource in a RESTful URL. `@RequestParam` extracts values from the query string (`?status=SHIPPED&page=0`) or from form-encoded request bodies, and supports default values and optionality via `required = false`/`defaultValue`. `@RequestBody` deserializes the entire HTTP request body — typically JSON — into a Java object using the configured `HttpMessageConverter` (Jackson by default), and is used for POST/PUT/PATCH payloads representing the resource being created or updated. Mixing these up is a common source of 400 errors: a client sending JSON when the endpoint expects `@RequestParam`, or vice versa, results in Spring being unable to bind the request correctly.

---

**Q16. How does ResponseEntity give you more control than returning a plain object from a controller method?**
Answer: When a controller method returns a plain object, Spring MVC serializes it to the response body and defaults to HTTP 200 (or 201 for methods with `@ResponseStatus`), with no direct way to vary the status code or headers based on runtime logic. `ResponseEntity<T>` wraps the body together with an explicit `HttpStatus` and an optional `HttpHeaders` object, letting the same method return `200 OK` with a body in the success case and `404 Not Found` with an empty body in the not-found case, or attach headers like `Location` after a resource creation. This is essential for correctly implementing REST semantics — for instance, a `POST` that creates a resource should return `201 Created` with a `Location` header pointing at the new resource's URI, which is only expressible cleanly via `ResponseEntity.created(uri).body(dto)`.

---

**Q17. What content negotiation does Spring MVC perform by default, and how can a client influence it?**
Answer: Spring MVC's `HttpMessageConverter` chain performs content negotiation to decide how to serialize the response body and how to deserialize the request body, based primarily on the `Accept` and `Content-Type` HTTP headers. By default with `spring-boot-starter-web`, Jackson's `MappingJackson2HttpMessageConverter` is registered and handles `application/json` in both directions; if a client sends `Accept: application/xml` and a JAXB/Jackson-XML converter is on the classpath, Spring will negotiate XML instead. A client can also influence negotiation via a format-specific URL suffix (deprecated in modern Spring) or explicitly via the `Accept` header, which is the recommended approach — relying on undocumented default behavior for content type is a frequent source of confusing 406 Not Acceptable errors when a client's `Accept` header doesn't match any registered converter.

---

**Q18. What is the purpose of Bean Validation (@Valid, @NotNull, @Size, etc.) and how does it integrate with Spring MVC?**
Answer: Bean Validation (JSR 380 / Jakarta Validation) lets you declare constraints directly on a DTO's fields — `@NotBlank`, `@Email`, `@Positive`, `@Size` — so that validation rules live next to the data they constrain rather than scattered through controller logic. When a controller parameter is annotated with `@Valid` (or `@Validated` for group-based validation) alongside `@RequestBody`, Spring MVC automatically triggers the validator before the method body executes; if any constraint fails, it throws `MethodArgumentNotValidException` before the controller method ever runs, which can then be caught centrally in a `@RestControllerAdvice` to produce a consistent structured error response. This keeps controller methods free of manual `if (dto.getEmail() == null) throw ...` boilerplate and ensures validation is applied uniformly across every endpoint that accepts the same DTO.

---

**Q19. What are Spring Boot starters and why do they matter for dependency management?**
Answer: A starter is a curated Maven/Gradle dependency descriptor — like `spring-boot-starter-web` or `spring-boot-starter-data-jpa` — that pulls in a coherent, version-compatible set of transitive dependencies for a specific capability, rather than requiring the developer to individually select and version-match dozens of libraries. `spring-boot-starter-web`, for example, brings in Spring MVC, an embedded Tomcat server, Jackson for JSON, and validation support in one declaration. Version compatibility across all of these is managed centrally by the Spring Boot BOM (`spring-boot-dependencies`), which the parent POM or `dependencyManagement` import pulls in, so upgrading the Spring Boot version in one place cascades correct, tested versions to every starter-provided dependency, eliminating a large class of dependency-hell version mismatches.

---

**Q20. What is the difference between an embedded server (like the default Tomcat in Spring Boot) and deploying a WAR to an external servlet container?**
Answer: Spring Boot's default packaging produces an executable "fat jar" with an embedded servlet container (Tomcat by default, swappable for Jetty or Undertow) bundled directly inside the artifact, so the application is started with `java -jar app.jar` and needs no separately installed application server — this is central to Boot's "just run it" philosophy and pairs naturally with containerized deployment (Docker) where the container image only needs a JVM. Deploying a WAR to an external container (like a standalone Tomcat or WildFly instance managed by ops) was the traditional Java EE model, requiring the war to be built with `spring-boot-maven-plugin`'s WAR packaging and the main class extending `SpringBootServletInitializer`. Most modern Spring Boot applications use the embedded-jar model exclusively, since it simplifies versioning (each app controls its own server version independent of other apps on the same host) and fits far more naturally into immutable-infrastructure and container-based deployment pipelines.

## Data Access, JPA & Transactions (Q21-Q30)

**Q21. What is the N+1 query problem and how does it typically manifest with Spring Data JPA?**
Answer: The N+1 problem occurs when code fetches a list of N parent entities with one query, and then, for each of the N parents, a *separate* query is lazily triggered to fetch an associated collection or reference — resulting in 1 + N total queries instead of one efficient join. It commonly manifests when a `@OneToMany` or `@ManyToOne` association is lazily loaded (the JPA default for collections, and a recommended override for `@ManyToOne`/`@OneToOne`) and the code iterates over a list of parents accessing the lazy association inside the loop, for example logging `order.getCustomer().getName()` for every order in a list returned by `findAll()`. It's especially insidious because it's invisible in a unit test with a handful of rows but degrades catastrophically at scale — 1,000 orders becomes 1,001 queries. Hibernate's `show-sql` or an APM tool will reveal a repeating identical query pattern, which is the telltale symptom to look for in a slow endpoint.

---

**Q22. What are the main strategies to fix or avoid the N+1 query problem in Spring Data JPA?**
Answer: The most direct fix is a JPQL `JOIN FETCH` in a custom repository query — `SELECT o FROM Order o JOIN FETCH o.customer WHERE o.status = :status` — which tells Hibernate to eagerly load the association in the same SQL query rather than lazily. `@EntityGraph` on a repository method achieves the same goal declaratively, letting you specify which lazy associations to eagerly fetch for that specific query without changing the entity's default fetch type globally. For simpler read-heavy DTO projections, Spring Data's projection interfaces or constructor expressions (`SELECT new com.app.OrderSummary(o.id, o.customer.name) FROM Order o`) sidestep the problem entirely by selecting only the needed columns via a join. Batch fetching (`@BatchSize` or `hibernate.default_batch_fetch_size`) is a lower-effort mitigation that groups the N lazy-load queries into fewer batched `IN (...)` queries when eager joining isn't practical.

---

**Q23. What is LazyInitializationException and when does it occur?**
Answer: `LazyInitializationException` is thrown when code attempts to access a lazily-loaded JPA association (like a `@ManyToOne` or `@OneToMany` collection) *after* the Hibernate `Session`/`EntityManager` that originally loaded the parent entity has already been closed — typically because the transaction that fetched the entity has already ended. This classically happens when a `@Service` method loads an entity inside a `@Transactional` boundary, returns it up to a `@Controller`, and the controller (or a JSON serializer running outside the transaction) then tries to access a lazy field for the response — the persistence context is gone by then, so Hibernate can't issue the lazy-load query and throws instead of silently failing. The fix is architectural: either eagerly fetch what the view layer needs within the transactional boundary (via `JOIN FETCH` or `@EntityGraph`), map to a DTO while still inside the transaction, or in tightly controlled cases extend the persistence context's scope (the "Open Session in View" pattern), which Spring Boot enables by default but which many teams deliberately disable because it hides the real problem and can cause its own performance issues.

---

**Q24. Why is @ManyToOne EAGER by default in JPA, and why is overriding it to LAZY considered best practice?**
Answer: The JPA specification defaults `@ManyToOne` and `@OneToOne` to `FetchType.EAGER` for historical reasons rooted in early JPA providers' assumptions, while `@OneToMany` and `@ManyToMany` default to `LAZY`. In practice, EAGER `@ManyToOne` associations are a major contributor to N+1 problems and unnecessary data loading because every time an entity is fetched — even via a simple `findById` — its eagerly-mapped associations are pulled in too, cascading potentially several joins deep if those associated entities themselves have eager relationships. The near-universal recommendation is to explicitly set `fetch = FetchType.LAZY` on every `@ManyToOne`/`@OneToOne` association and load associations explicitly and intentionally via `JOIN FETCH`/`@EntityGraph` only where actually needed, giving the developer full control over what data is fetched per query rather than relying on JPA's default cascade of implicit joins.

---

**Q25. Explain @Transactional propagation REQUIRED vs REQUIRES_NEW with a concrete example of when the difference matters.**
Answer: With `REQUIRED` (the default), if method A calls method B and both are `@Transactional`, B simply joins A's existing transaction — there's only ever one physical database transaction, and if either method throws an exception causing a rollback, the entire combined unit of work rolls back together. With `REQUIRES_NEW`, calling B suspends A's transaction and starts a genuinely independent one that commits or rolls back on its own, completely separate from whatever happens in A afterward. This distinction matters concretely for audit logging: if you want an audit record to persist even when the main business operation later fails and rolls back, the audit-writing method needs `REQUIRES_NEW` so its commit is durable regardless of A's outcome — with `REQUIRED`, the audit record would be rolled back right along with the failed business operation since they'd share the same transaction.

---

**Q26. Why does calling a @Transactional method from another method in the same class silently not start a transaction?**
Answer: Spring's declarative transaction management is implemented via AOP proxies — by default, either a JDK dynamic proxy (if the bean implements an interface) or a CGLIB subclass proxy (if it doesn't) wraps the actual bean, and the proxy is what intercepts calls to `@Transactional` methods and wraps them in transaction begin/commit/rollback logic. This interception only happens when the call comes through the proxy from *outside* the object — when code inside the same class calls `this.someTransactionalMethod()`, that's a plain Java method call on the raw `this` reference, which never passes through the surrounding proxy, so none of the transactional advice runs and the method executes with no transaction at all. This is one of the most common real-world Spring bugs; the practical fixes are to move the called method into a separate `@Service` bean and inject that bean, or to inject a self-reference of the proxy (e.g., via `ApplicationContext.getBean` or `@Lazy` self-autowiring) and call through that instead of `this`.

**Q27. What is optimistic locking in JPA and how does @Version implement it?**
Answer: Optimistic locking assumes conflicts between concurrent transactions are rare, so instead of holding a database lock for the duration of a read-modify-write cycle (pessimistic locking), it detects conflicts only at write time. Adding a `@Version` field (typically a `Long` or `int`) to an entity causes Hibernate to include `WHERE version = ?` in every `UPDATE` statement and increment the version column on each successful write; if another transaction updated the row in between — changing its version — the `UPDATE` affects zero rows, and Hibernate detects this and throws `OptimisticLockException`. This is far cheaper than pessimistic locking (`SELECT ... FOR UPDATE`) under low-contention workloads because it never blocks readers or writers waiting for a lock, at the cost of needing application-level retry or user-facing conflict-resolution logic when the rare collision does occur.

**Q28. What is the difference between JPQL and native SQL queries in Spring Data, and when would you reach for native queries?**
Answer: JPQL (`@Query("SELECT o FROM Order o WHERE ...")`) operates on the entity object model — it references entity class names and field names rather than table and column names, and Hibernate translates it into dialect-appropriate SQL at runtime, which keeps queries portable across different database vendors and lets results map directly back to entities or DTOs via constructor expressions. Native queries (`@Query(value = "...", nativeQuery = true)`) are raw SQL passed straight through to the database driver, useful when you need database-specific features JPQL can't express — window functions, recursive CTEs, full-text search operators, vendor-specific hints, or complex aggregations that are painful to model in JPQL. The tradeoff is that native queries lose portability across database vendors and bypass some of Hibernate's automatic entity-state tracking, so they're best reserved for genuinely SQL-specific needs rather than used as a default escape hatch from learning JPQL.

---

**Q29. How does pagination work with Spring Data JPA's Pageable and Page abstractions?**
Answer: A repository method that accepts a `Pageable` parameter (typically constructed via `PageRequest.of(pageNumber, pageSize, sort)`) and returns `Page<T>` gets automatic, correct pagination handling from Spring Data — it issues the paginated `SELECT ... LIMIT ... OFFSET ...` query for the requested page and, because `Page` extends `Slice`, also issues a separate `COUNT(*)` query to populate `getTotalElements()`/`getTotalPages()`, letting the client render page navigation. If you don't need the total count (for infinite-scroll UIs, for instance), returning `Slice<T>` instead avoids the extra count query entirely, which is a worthwhile optimization on large tables where `COUNT(*)` itself is expensive. Sorting is expressed via `Sort.by("field").descending()` composed into the `Pageable`, and Spring Data automatically appends the corresponding `ORDER BY` clause to the generated query.

---

**Q30. What is JPA auditing (@CreatedDate, @LastModifiedDate, @CreatedBy) and what do you need to enable it?**
Answer: Spring Data JPA auditing automatically populates timestamp and user-tracking fields on entities without any manual code in the service layer, using `@CreatedDate` and `@LastModifiedDate` for automatic timestamps, and `@CreatedBy`/`@LastModifiedBy` for the identity of the acting user. To activate it, the entity class must be annotated `@EntityListeners(AuditingEntityListener.class)` (or extend a shared `@MappedSuperclass` base with the audit fields already annotated), and the application must enable `@EnableJpaAuditing` on a `@Configuration` class. For the `@CreatedBy`/`@LastModifiedBy` fields to know who the current user is, you also need to provide an `AuditorAware<T>` bean whose `getCurrentAuditor()` method typically pulls the username from the Spring Security `SecurityContextHolder`. This is a clean example of cross-cutting concerns handled declaratively rather than scattered as `entity.setUpdatedAt(Instant.now())` calls throughout every service method.

## Exception Handling & Spring Security (Q31-Q40)

**Q31. How does @ControllerAdvice centralize exception handling, and how does it interact with @ExceptionHandler on individual controllers?**
Answer: `@ControllerAdvice` (or `@RestControllerAdvice` for REST APIs, which also adds `@ResponseBody`) designates a class whose `@ExceptionHandler` methods apply globally across every controller in the application, rather than needing identical `@ExceptionHandler` methods duplicated in every controller class. Spring resolves the most specific matching handler when an exception propagates out of a controller method: if the throwing controller itself has a matching `@ExceptionHandler`, that local handler takes precedence over the equivalent handler in a `@ControllerAdvice`; only if no local handler matches does Spring fall back to the global advice. This pattern typically produces one `GlobalExceptionHandler` class mapping domain exceptions (`ResourceNotFoundException` → 404, `MethodArgumentNotValidException` → 400) to consistent, structured error responses, keeping individual controllers free of repetitive try/catch or handler boilerplate.

---

**Q32. What is ProblemDetail (RFC 7807) and why did Spring Boot 3 adopt it over ad-hoc error response formats?**
Answer: `ProblemDetail` is Spring's built-in implementation of RFC 7807 ("Problem Details for HTTP APIs"), a standardized JSON structure for error responses containing fields like `type`, `title`, `status`, `detail`, and `instance`, plus support for arbitrary extension properties via `setProperty()`. Before its introduction, every team invented its own bespoke error JSON shape, meaning API consumers had to learn a different error contract per service and per team, and tooling couldn't generically reason about error responses. By standardizing on `ProblemDetail`, Spring Boot 3 lets `@ExceptionHandler` methods return a self-describing, spec-compliant error body via `ProblemDetail.forStatusAndDetail(status, message)`, which API gateways, client SDKs, and monitoring tools can parse uniformly, and it integrates automatically with Spring MVC's default exception handling for common exceptions if you don't write a custom handler at all.

---

**Q33. Walk through what happens, step by step, when a request hits a Spring Security-secured endpoint with the SecurityFilterChain DSL.**
Answer: The request first passes through the servlet container's filter chain, where Spring Security has inserted its own `FilterChainProxy`, which delegates to the ordered list of security filters configured in the `SecurityFilterChain` bean. Authentication filters run first — for a JWT-based stateless API, a custom filter added via `.addFilterBefore(jwtAuthFilter, UsernamePasswordAuthenticationFilter.class)` extracts and validates the bearer token, and on success populates the `SecurityContextHolder` with an `Authentication` object representing the caller. Later in the chain, the authorization stage evaluates the `authorizeHttpRequests` rules in the order they were declared — first matching rule wins — checking the current `Authentication`'s roles/authorities against the required ones for that request pattern; if authorization fails, an `AccessDeniedException` is thrown and handled by the configured `accessDeniedHandler`. Only if authentication succeeded and authorization rules pass does the request proceed to the actual `DispatcherServlet` and controller method.

**Q34. Why is CSRF protection typically disabled for stateless JWT-based REST APIs, and is that actually safe?**
Answer: CSRF (Cross-Site Request Forgery) attacks exploit the browser's automatic inclusion of cookies on cross-origin requests — a malicious site can trigger a request to your API and the browser will attach the victim's session cookie automatically, so the server needs a CSRF token to verify the request genuinely originated from your own frontend. Stateless JWT APIs typically don't rely on cookies for authentication at all — the token is sent explicitly in an `Authorization: Bearer` header by client-side JavaScript, which a malicious third-party page cannot forge because it has no way to read or attach another origin's `Authorization` header (unlike cookies, which browsers attach automatically) — so the CSRF attack vector genuinely doesn't apply, and disabling `csrf()` is safe. This reasoning only holds as long as the JWT is never also stored in a cookie that gets sent automatically; if a team switches to storing the JWT in an HttpOnly cookie for XSS mitigation, CSRF protection needs to come back, because now the browser will attach it automatically to cross-origin requests again.

**Q35. What does @EnableMethodSecurity enable, and how does @PreAuthorize differ from @PostAuthorize?**
Answer: `@EnableMethodSecurity` activates Spring Security's method-level authorization annotations (`@PreAuthorize`, `@PostAuthorize`, `@PreFilter`, `@PostFilter`) by installing AOP interceptors around annotated methods, functioning through the same dynamic-proxy mechanism as `@Transactional`. `@PreAuthorize` evaluates its SpEL expression *before* the method executes and throws `AccessDeniedException` immediately if it evaluates to false, meaning the method body never runs at all if authorization fails — appropriate for role checks like `hasRole('ADMIN')` that don't depend on the method's result. `@PostAuthorize` evaluates its expression *after* the method has already executed, with access to `returnObject` in the SpEL expression, which is necessary when the authorization decision depends on data only available in the result — for example, verifying that the returned order actually belongs to the requesting user — but note that the method's side effects (including any writes) have already happened by the time authorization is checked, so `@PostAuthorize` is unsuitable for guarding mutating operations.

**Q36. Why does @PreAuthorize silently fail to protect a method when it's called via self-invocation, and what's the real-world impact?**
Answer: Exactly like `@Transactional` and `@Cacheable`, `@PreAuthorize` is implemented through an AOP proxy wrapping the bean — the security check is advice woven around calls that arrive through that proxy. When a method inside the same class calls another `@PreAuthorize`-protected method via a bare `this.method()` call, that invocation never passes through the proxy, so the authorization check is completely skipped and the method executes unconditionally regardless of the caller's roles. This is a genuinely dangerous gotcha in production because it's a silent security bypass rather than a visible bug — code reviewers see the `@PreAuthorize` annotation present and assume the method is protected, while in reality any code path that reaches it via internal self-invocation sails through with no authorization check at all. The mitigation is identical to the `@Transactional` case: refactor the protected logic into a separate bean invoked externally, or restructure the call path so cross-cutting-concern-guarded methods are never called from within the same class.

**Q37. What is a JWT and what should a Spring Boot backend actually validate when receiving one?**
Answer: A JWT (JSON Web Token) is a compact, self-contained token consisting of a Base64URL-encoded header, payload (claims like `sub`, `exp`, `iat`, custom roles), and a cryptographic signature, all concatenated and dot-separated — the signature lets a receiving server verify the token hasn't been tampered with, without needing to look it up in a database. A correctly implemented validation filter must check the signature against the expected signing key/algorithm (rejecting tokens claiming `alg: none`, a classic JWT vulnerability), verify the `exp` claim hasn't passed and, if present, that `nbf` (not-before) has, confirm the `iss` (issuer) and `aud` (audience) claims match expected values if used, and only then trust the claims to build the `Authentication` object. A common and serious mistake is decoding the JWT payload and trusting its claims (like a `role` field) without first verifying the signature — since the payload is only Base64-encoded, not encrypted, anyone can forge arbitrary claims in an unsigned or signature-unverified token.

**Q38. What's the difference between authentication and authorization in the context of the SecurityFilterChain, and where does each happen?**
Answer: Authentication answers "who is making this request" — establishing and verifying the caller's identity, whether via username/password, a JWT signature check, an API key, or an OAuth2 token introspection — and results in a populated `Authentication` object stored in the `SecurityContextHolder`. Authorization answers "is this identified caller allowed to do this specific thing" — evaluating the caller's granted authorities/roles against the access rules declared for the requested resource, via `authorizeHttpRequests` matchers at the request level or `@PreAuthorize`/`@PostAuthorize` at the method level. In the filter chain, authentication filters run first (they must establish who the caller is before any authorization decision can be made), and authorization is evaluated afterward — often at two layers, coarse-grained URL-pattern rules in the `SecurityFilterChain` for broad access control, and fine-grained method-level checks for business-specific rules that can't be expressed as a simple URL pattern.

**Q39. How does password encoding with BCryptPasswordEncoder work, and why shouldn't passwords ever be stored as plain hashes (like plain SHA-256)?**
Answer: `BCryptPasswordEncoder` implements the bcrypt algorithm, which incorporates a random salt automatically generated per password and a configurable, deliberately expensive work factor (the "cost" or number of hashing rounds, typically 10-12), producing an encoded string that embeds both the salt and cost alongside the hash itself, so verification (`matches()`) can recompute correctly without needing a separately stored salt column. Plain fast hashes like unsalted SHA-256 are unsuitable for password storage because they're designed for speed, which is precisely the wrong property for password hashing — modern GPUs can compute billions of SHA-256 hashes per second, making brute-force and rainbow-table attacks against a leaked hash database practical within hours, whereas bcrypt's deliberate slowness and per-password salt make both rainbow tables (defeated by the salt) and brute-forcing (defeated by the cost factor) computationally infeasible at scale. This is why Spring Security's default `PasswordEncoder` recommendation has consistently been bcrypt (or newer alternatives like Argon2) rather than any general-purpose fast hash function.

**Q40. What security risks does exposing Actuator endpoints introduce in production, and how do you mitigate them?**
Answer: Actuator endpoints like `/actuator/env` (environment properties, though sensitive values are sanitized by default), `/actuator/heapdump` (a full JVM heap dump that can contain in-memory secrets, session tokens, or PII), `/actuator/beans`, and `/actuator/shutdown` expose deep operational and potentially sensitive information about the running application, and if left unsecured on a public-facing port, hand an attacker a detailed map of the application's internals or, in the case of `/shutdown`, a trivial denial-of-service vector. Mitigation requires securing Actuator explicitly within the `SecurityFilterChain` — typically restricting `/actuator/**` (except perhaps `/actuator/health`) to an internal network, a separate management port (`management.server.port`), and requiring authentication/authorization for anything beyond a bare health check — combined with `management.endpoints.web.exposure.include` being scoped to only the specific endpoints actually needed rather than `include: "*"`, and `/actuator/shutdown` disabled unless there's a specific, tightly controlled operational reason to expose it.

## Testing, Caching, Async & Microservices (Q41-Q50)

**Q41. What's the practical difference between @SpringBootTest, @WebMvcTest, and @DataJpaTest, and when should you use each?**
Answer: `@SpringBootTest` boots the entire `ApplicationContext` — every bean, every auto-configuration, optionally a real embedded server with `webEnvironment = RANDOM_PORT` — making it the slowest but most realistic option, appropriate for true end-to-end integration tests that exercise the full stack including security filters and real (or Testcontainers-backed) database interactions. `@WebMvcTest(SomeController.class)` loads only the web layer — the specified controller, `@ControllerAdvice` classes, filters, and MVC infrastructure — while explicitly excluding `@Service`/`@Repository` beans, which must be supplied as `@MockBean`s; this makes controller tests fast and focused purely on request mapping, serialization, and validation behavior. `@DataJpaTest` loads only JPA-related configuration plus an embedded or Testcontainers database, auto-configures a `TestEntityManager`, and wraps each test in a transaction that's rolled back afterward, making it ideal for testing repository queries in isolation without the overhead of the full application context.

---

**Q42. What is the difference between @Mock/@InjectMocks (pure Mockito) and @MockBean (Spring Boot Test)?**
Answer: `@Mock` and `@InjectMocks`, used with `@ExtendWith(MockitoExtension.class)`, operate entirely outside of Spring — Mockito creates a mock object and injects it via reflection into the field of a manually-instantiated class under test, with no `ApplicationContext` involved at all, making these tests extremely fast pure unit tests. `@MockBean` is a Spring Boot Test feature that requires an active `ApplicationContext` (via `@SpringBootTest`, `@WebMvcTest`, etc.) — it replaces the real bean of that type in the context with a Mockito mock, which is essential when you need to test a component (like a controller) that Spring itself constructs and wires, but want to isolate it from one of its real collaborators. The rule of thumb is to default to plain Mockito (`@Mock`/`@InjectMocks`) for service- and component-level unit tests since they don't need a Spring context at all, and reserve `@MockBean` for cases where the class under test is genuinely instantiated by Spring, such as controller tests under `@WebMvcTest`.

---

**Q43. What are Testcontainers and why are they preferred over an embedded/in-memory database (like H2) for repository integration tests?**
Answer: Testcontainers is a library that spins up real Docker containers — an actual PostgreSQL, MySQL, or Kafka instance — for the duration of a test run, and tears them down automatically afterward, giving tests a database that behaves identically to production rather than an approximation. H2 in in-memory mode is fast and requires no Docker, but it doesn't perfectly replicate every SQL dialect quirk, function, constraint behavior, or index/locking semantics of the actual production database (PostgreSQL and H2 diverge meaningfully on things like JSON columns, certain date functions, and specific constraint violation error codes), which means tests can pass against H2 and then fail against real PostgreSQL in production, or worse, silently mask a bug that only manifests on the real engine. `@Testcontainers` combined with `@Container` and `@DynamicPropertySource` (to inject the container's dynamically-assigned JDBC URL into Spring's `DataSource` configuration at test time) gives you the confidence of testing against the real database engine at the cost of somewhat slower test startup, which is usually a worthwhile tradeoff for repository and integration-level tests.

**Q44. Explain why calling an @Async method from within the same class silently executes it synchronously instead of asynchronously.**
Answer: `@Async`, like `@Transactional` and `@Cacheable`, is implemented via an AOP proxy that Spring wraps around the bean — the proxy's advice is what actually submits the method invocation to a `TaskExecutor` thread pool and immediately returns a `Future`/`CompletableFuture` to the caller. When code inside the same class invokes an `@Async` method through a bare `this.method()` call, the call bypasses the surrounding proxy entirely and directly invokes the raw method on the current thread, meaning it runs synchronously and blocks the caller just like a normal method call, silently defeating the entire purpose of `@Async` with no error or warning at all. The practical consequence is a class that appears to fire background work but is actually blocking on every "async" call whenever the async method is invoked from a sibling method in the same class — the fix is the same pattern as the `@Transactional` self-invocation issue: split the async method into a separate bean and inject/call it externally.

**Q45. Walk through what @Cacheable actually does on a cache hit versus a cache miss, and what pitfall exists with mutable cached objects.**
Answer: On a cache miss — the computed cache key (by default derived from the method's arguments, or explicitly via the `key` SpEL expression) isn't present in the configured cache — the AOP proxy lets the real method execute, captures its return value, and stores it in the cache under that key before returning it to the caller. On a cache hit, the proxy intercepts the call before the real method body ever runs, looks up the key, and returns the cached value directly, entirely skipping the (often expensive) method logic — this is the whole performance benefit, but it means side effects inside the method body (like incrementing a counter or writing an audit log) silently don't happen on cache hits, which is easy to overlook. The mutable-object pitfall: if the cached value is a mutable object and a caller mutates it after retrieving it from the cache (e.g., modifying a `List` field on a cached DTO), that mutation corrupts the shared cached instance for every subsequent caller that hits the same cache key, since most cache implementations store a reference rather than a defensive copy — the safe pattern is to only cache immutable objects/records or DTOs that callers treat as read-only.

**Q46. What is the difference between fixedRate and fixedDelay in @Scheduled, and why does that distinction matter for a long-running job?**
Answer: `fixedRate` measures the interval from the *start* of one execution to the start of the next, so if a job configured with `fixedRate = 60000` takes 90 seconds to run, Spring will attempt to trigger the next execution the moment the 60-second mark passes — by default `@Scheduled` methods run on a single-threaded scheduler, so that next execution is simply queued and starts immediately after the previous one finishes rather than causing genuine overlapping execution, but the *intended* cadence is violated because runs effectively become back-to-back rather than 60 seconds apart. `fixedDelay` measures the interval from the *end* of one execution to the start of the next, guaranteeing a full quiescent gap between runs regardless of how long each execution takes — this is the safer choice for jobs whose duration is variable or can occasionally spike, since it prevents runs from ever queuing up or piling on top of each other. For any job where the individual work duration might approach or exceed the configured interval, `fixedDelay` is almost always the more predictable and safer choice.

**Q47. What does WebClient offer over the older RestTemplate, and why is RestTemplate now in maintenance mode?**
Answer: `RestTemplate` is a synchronous, blocking HTTP client — each call blocks the calling thread until the full response is received, which doesn't scale well under high concurrency because each in-flight request ties up a thread for its entire duration. `WebClient`, part of Spring WebFlux, is a fully non-blocking, reactive HTTP client built on Project Reactor's `Mono`/`Flux` types, letting a small, fixed thread pool handle a much larger number of concurrent in-flight requests since threads aren't blocked waiting on I/O — it also composes naturally with reactive pipelines (`.flatMap`, `.retry`, `.timeout`) for expressing retries, timeouts, and fallback logic declaratively. Spring officially placed `RestTemplate` in maintenance mode specifically to focus future HTTP client development on `WebClient` (and, in Spring 6+, the newer `RestClient` for teams wanting a fluent synchronous API without adopting reactive types), so new code — including synchronous callers — is generally steered toward `WebClient` or `RestClient` rather than `RestTemplate`.

**Q48. What problem does Resilience4j's circuit breaker pattern solve in a microservices call chain, and what are its basic states?**
Answer: In a chain of service-to-service calls, if a downstream service becomes slow or unresponsive, callers that keep retrying or waiting on it can exhaust their own thread pools and connection resources, causing the failure to cascade upstream through the entire call chain — a small outage in one service can take down the whole system. A circuit breaker wraps calls to a potentially unreliable dependency and tracks the failure rate over a sliding window; in the **CLOSED** state, calls pass through normally while failures are tracked; once the failure rate crosses a configured threshold, the breaker trips to **OPEN**, immediately failing (or falling back) all calls without even attempting the real request for a configured wait duration, giving the downstream service time to recover instead of being hammered by continued traffic. After the wait duration elapses, the breaker moves to **HALF_OPEN**, allowing a limited number of trial calls through — if they succeed, it returns to CLOSED; if they still fail, it reopens — and Resilience4j lets you pair this with a `@CircuitBreaker` annotation and a `fallbackMethod` to return a degraded but graceful response instead of propagating the failure.

**Q49. What is Spring Cloud Config and what problem does centralized configuration solve for microservices?**
Answer: In a microservices architecture with many independently deployable services, managing environment-specific configuration (database URLs, feature flags, API keys) separately per service via local property files becomes unmanageable — changes require redeploying services just to update a config value, and there's no single source of truth for what configuration is actually running where. Spring Cloud Config Server centralizes configuration in a version-controlled backend (typically a Git repository), and client services fetch their configuration from the Config Server at startup (or dynamically refresh it via the `/actuator/refresh` endpoint combined with `@RefreshScope` on beans that need to pick up new values without a restart), giving operators one place to view and change configuration across the whole fleet, full audit history of configuration changes via Git commits, and the ability to promote the same configuration through environments in a controlled, reviewable way.

**Q50. What is the difference between client-side and server-side service discovery, and how does Spring Cloud typically implement it?**
Answer: In server-side discovery, a client makes a request to a well-known load balancer or gateway endpoint, and that intermediary is responsible for looking up a healthy service instance and routing the request — the client never needs to know about individual instance addresses at all. In client-side discovery — the more common Spring Cloud pattern, implemented with Netflix Eureka or Consul as the registry — each service instance registers itself with the discovery server on startup (and sends periodic heartbeats), and calling services query the registry (often transparently, via a Spring Cloud LoadBalancer-aware `WebClient`/`RestTemplate` using a logical service name like `http://order-service/api/orders` instead of a hardcoded host:port) to get a current list of healthy instances and pick one, typically via round-robin. Client-side discovery avoids the extra network hop through a central load balancer for every call, at the cost of pushing more responsibility (registry client libraries, load-balancing logic) into every service, whereas server-side discovery centralizes that complexity at the cost of an additional infrastructure component and hop.
