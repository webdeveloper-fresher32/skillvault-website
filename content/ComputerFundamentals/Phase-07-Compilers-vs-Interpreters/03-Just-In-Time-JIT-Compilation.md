## 1. The Problem JIT Solves

Pure interpretation is portable and starts instantly, but slow in steady state — every time a line of bytecode runs, the VM re-dispatches to the right handler, re-decodes operands, etc. Ahead-of-time (AOT) compilation to native code is fast in steady state but requires a separate build step and produces platform-specific binaries.

**JIT (Just-In-Time) compilation** tries to get the best of both: start by interpreting bytecode (fast startup, portable), but **watch the program as it runs**, and compile the parts that run a lot ("hot" code) into native machine code on the fly — while the program is still running.

```
Pure interpretation:     bytecode ──▶ interpreted forever, every single time
AOT compilation:         source ──▶ native code, compiled once, before running, never re-translated
JIT compilation:         bytecode ──▶ interpreted at first ──▶ hot paths detected ──▶
                                        compiled to native code MID-EXECUTION ──▶ native code used from then on
```

## 2. How JIT Compilation Works Conceptually

```
┌─────────────────────────────────────────────────────────────────────────┐
│                         JIT Execution Timeline                          │
│                                                                           │
│  1. Source compiled to bytecode (fast, ahead of time or on load)        │
│         │                                                                │
│         ▼                                                                │
│  2. VM starts INTERPRETING bytecode immediately (program runs right away)│
│         │                                                                │
│         ▼                                                                │
│  3. VM's PROFILER counts how often each function/loop executes          │
│         │                                                                │
│         ▼                                                                │
│  4. A function crosses a "hot" threshold (e.g., called 1000+ times)     │
│         │                                                                │
│         ▼                                                                │
│  5. JIT COMPILER kicks in: compiles that hot bytecode to native code,   │
│     applying optimizations based on OBSERVED runtime behavior           │
│     (actual types seen, actual branches taken)                          │
│         │                                                                │
│         ▼                                                                │
│  6. Future calls to that function jump straight to the native code      │
│     — no more interpretation overhead for that function                 │
│         │                                                                │
│         ▼                                                                │
│  7. (Advanced JITs) If runtime assumptions turn out wrong later          │
│     (e.g., a variable's type changes), DEOPTIMIZE back to interpreting  │
│     and re-JIT with updated assumptions                                 │
└─────────────────────────────────────────────────────────────────────────┘
```

The key insight: a JIT compiler has information an AOT compiler never has — **actual runtime behavior**. It knows which branch of an `if` is taken 99% of the time, which concrete types flow through a function, which loops run a billion iterations vs. three. It uses that observed information to generate highly specialized, fast native code for exactly the patterns the program actually exhibits.

## 3. Example: V8 and JavaScript

V8 (Google's JavaScript engine, used in Chrome and Node.js) is a textbook multi-tier JIT:

```
JavaScript source
      │
      ▼  Parser
   Bytecode (generated by "Ignition", V8's interpreter/bytecode compiler)
      │
      ▼  Ignition INTERPRETS the bytecode immediately — code runs right away
      │
      ▼  V8 profiles execution: which functions are called a lot? which object
         shapes/types show up repeatedly?
      │
      ▼  Hot functions get sent to "TurboFan", V8's optimizing JIT compiler
   Highly optimized native machine code (specialized for the types actually observed)
      │
      ▼  If assumptions break (e.g., a function suddenly receives an object of a
         different "shape" than before), TurboFan's output is discarded
         ("deoptimization") and execution falls back to Ignition's bytecode,
         possibly re-optimizing later with new assumptions
```

This is why the classic advice "keep object shapes consistent" and "avoid changing a variable's type" makes JavaScript faster: it lets TurboFan's optimizations stay valid instead of triggering deoptimization.

## 4. Example: PyPy and Python

Standard CPython (the reference Python implementation) has **no JIT** by default — it compiles to bytecode and pure-interprets it, which is a major reason Python is slower than JavaScript for CPU-bound work.

**PyPy** is an alternative Python implementation that adds a JIT compiler:

```
Python source
      │
      ▼  PyPy's compiler produces bytecode (similar idea to CPython's .pyc)
      │
      ▼  PyPy's interpreter runs the bytecode, tracing execution
      │
      ▼  PyPy detects "hot loops" (a specific technique called tracing JIT:
         it records the actual sequence of operations executed in a loop)
      │
      ▼  The trace is compiled to native machine code, specialized for the
         types/values actually observed during that trace
      │
      ▼  Subsequent iterations of that loop run the native trace directly
```

Because of this, PyPy can run pure-Python CPU-bound benchmarks many times faster than CPython — often cited as roughly 4-10x on numeric/loop-heavy code, though the exact number varies enormously by workload. PyPy is slower to "warm up" than CPython on short-lived scripts, and can even be slower for tiny scripts where the JIT never gets a chance to pay off its own compilation cost.

## 5. Why JIT Can Outperform Pure Interpretation

1. **Eliminates repeated dispatch overhead** — a pure interpreter re-decodes and re-dispatches every bytecode instruction every single time it runs; JIT-compiled native code has none of that overhead once compiled.
2. **Specializes based on observed types/values** — a JIT can generate code assuming "this variable is always an integer here" (because that's what it's observed), skipping generic type-checking machinery a naive interpreter must always perform.
3. **Applies classic optimizations at the machine-code level** — inlining, register allocation, loop-invariant code motion — the same techniques an AOT compiler uses, but informed by real execution data.
4. **Only pays the compilation cost for code that matters** — cold code (run once, e.g., startup logic) stays interpreted, cheaply; only hot code (run millions of times) earns the investment of JIT compilation.

## 6. Why JIT Is Slower to Start Than Pure Interpretation

```
Pure interpretation startup:
  parse ──▶ bytecode ──▶ start interpreting IMMEDIATELY

JIT startup:
  parse ──▶ bytecode ──▶ start interpreting IMMEDIATELY (same as above, no penalty yet)
     ... but then, additionally, while running:
  profiler overhead (counting calls/iterations, tracking observed types)
     +
  JIT compilation cost itself (an actual compile pass — lexing-free, but still
  code generation and optimization — happens WHILE the program is trying to run)
     +
  possible deoptimization cost (discarding bad guesses and falling back)
```

None of this is free — profiling every function call and loop iteration costs CPU cycles, and compiling to native code mid-execution is itself real compiler work happening on the critical path. That's why JIT-based runtimes (JVM, V8, PyPy) tend to have worse startup latency and worse performance on very short-lived scripts than a pure interpreter — the JIT hasn't had time to identify hot code and compile it before the program already finished. This is precisely why serverless/CLI tools sometimes prefer AOT-compiled languages (Go) or lightweight interpreters over JIT-heavy runtimes: for code that runs once and exits, JIT's long-term payoff never materializes, only its upfront cost does.

```
Short-lived script (runs for 50ms total):
  JIT runtime: interpret (works fine) — JIT never gets to kick in — no benefit, no real harm
  Long-running server (runs for days, same hot loop executed billions of times):
  JIT runtime: interpret briefly ──▶ JIT-compile hot loop ──▶ near-native speed for the
               remaining billions of iterations — huge net win
```

## 7. AOT vs Interpreted vs JIT — Full Picture

| Approach | Startup | Steady-state speed | Adapts to runtime behavior? | Examples |
|---|---|---|---|---|
| **AOT compiled** | Fast (binary runs immediately; compile step is separate/offline) | Fastest, consistently | No — optimizes only on static, compile-time information | C, C++, Go, Rust |
| **Pure interpreted** | Fastest (no compile step at all) | Slowest | No | Bash, naive tree-walking interpreters |
| **JIT (bytecode + adaptive compilation)** | Slower than pure interpretation (profiling + compilation overhead), faster than full AOT of a huge program | Can approach or match AOT once warmed up | Yes — specializes based on observed types/branches | V8 (JS), JVM (Java), PyPy (Python), .NET CLR (C#) |

## 9. Interview Q&A

**Q: What is JIT compilation, in one sentence?**
Answer: JIT (Just-In-Time) compilation is a runtime technique where a virtual machine starts by interpreting bytecode for fast startup, but profiles execution to detect frequently run ("hot") code and compiles just that code into native machine code while the program is still running, so future executions of it run at near-native speed.

**Q: Why can JIT-compiled code sometimes outperform even ahead-of-time compiled code?**
Answer: A JIT compiler has access to actual runtime information — the real types flowing through a function, which branches are actually taken, which loops run the most — that an ahead-of-time compiler, working only from static source code, cannot know. This lets the JIT generate highly specialized code for the exact patterns the program exhibits in practice, sometimes producing more effective optimizations than a generic ahead-of-time compilation of the same source.

**Q: Why does JIT have worse startup performance than pure interpretation?**
Answer: JIT adds overhead that pure interpretation doesn't have: continuously profiling code to detect hot paths, and then performing an actual compilation pass (code generation and optimization) to native machine code while the program is already running. For short-lived programs, this overhead is pure cost with no payoff, because the program finishes before the JIT-compiled code gets a chance to run enough times to offset the compilation cost.

**Q: Give a concrete example of a JIT compiler and how it's structured.**
Answer: V8, the JavaScript engine used in Chrome and Node.js, uses a two-tier design: Ignition compiles JavaScript to bytecode and interprets it immediately for fast startup, while profiling execution. Frequently executed functions get compiled by TurboFan, V8's optimizing JIT, into native machine code specialized for the observed types. If those type assumptions are later violated, TurboFan's output is discarded (deoptimization) and execution falls back to Ignition's bytecode.

**Q: What is deoptimization and why does it matter for JIT performance?**
Answer: Deoptimization is when a JIT compiler discards previously JIT-compiled native code because a runtime assumption it relied on (e.g., "this variable is always a number") turned out to be false, forcing execution to fall back to the slower interpreted or re-compiled path. It matters because writing code that changes types or object shapes unpredictably can repeatedly trigger deoptimization, erasing the performance benefit JIT is supposed to provide — this is the technical reason behind advice like "keep your JavaScript object shapes consistent."

**Q: Why doesn't CPython use JIT compilation by default, and what's the alternative that does?**
Answer: Standard CPython is a straightforward bytecode interpreter with no JIT, prioritizing simplicity, portability, and C-extension compatibility over raw execution speed. PyPy is an alternative Python implementation that adds a tracing JIT compiler, detecting hot loops and compiling them to native code, which can make CPU-bound pure-Python code run substantially faster than CPython — at the cost of slower startup and less compatibility with some C-extension-heavy libraries.
