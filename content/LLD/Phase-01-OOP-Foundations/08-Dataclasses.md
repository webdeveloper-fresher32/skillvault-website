## 1. From Boilerplate POJOs to Modern Java Records

- Historically, representing a plain immutable Data Transfer Object (DTO) or Value Object in Java required 60+ lines of verbose code:
- Private final fields
- Full parameter constructor
- Getters for every field
- `equals()` and `hashCode()`
- `toString()`

With **Java 14+ Records**, this entire block is reduced to **one single declarative line**:

```java
public record Coordinates(double latitude, double longitude) {}
```

---

## 2. Anatomy of a Java Record

A record is a special class that acts as a transparent carrier for immutable data:

- Fields are implicitly `private final`.
- Accessor methods match field names directly (`point.latitude()`, not `point.getLatitude()`).
- The class is implicitly `final` (cannot be extended).
- Canonical constructor and implementations for `equals()`, `hashCode()`, and `toString()` are automatically generated by the compiler.

---

## 3. Compact Constructors & Business Validation

The compact constructor omits the parameter list and allows modifying or validating parameters before assignment to `this.*`:

```java
public record CurrencyAmount(double amount, String currency) {
    public CurrencyAmount {
        if (amount < 0) {
            throw new IllegalArgumentException("Amount cannot be negative: " + amount);
        }
        if (currency == null || currency.length() != 3) {
            throw new IllegalArgumentException("Invalid ISO currency code: " + currency);
        }
        currency = currency.toUpperCase(); // Parameter normalization
    }
}
```

## 4. Custom Methods & Interface Implementation in Records

Records can implement interfaces, declare static fields/methods, and define helper instance methods:

```java
public interface Priceable {
    double getPriceInUsd();
}

public record CartItem(String sku, int quantity, double unitPrice) implements Priceable {
    @Override
    public double getPriceInUsd() {
        return quantity * unitPrice;
    }

    public boolean isBulkDiscountEligible() {
        return quantity >= 10;
    }
}
```

## 5. When to Use Records vs Standard Classes

| Scenario                                                                |   Record (`record`)   |   Standard Class (`class`)   |
| :---------------------------------------------------------------------- | :----------------------: | :-----------------------------: |
| **DTOs / API Payloads**                                           |         ✅ Ideal         |         ❌ Too verbose         |
| **Domain Value Objects (Money, Address, GeoPoint)**               |         ✅ Ideal         | ❌ Prone to accidental mutation |
| **Stateful Entities with mutable lifecycles (User, Order, Room)** |     ❌ Cannot mutate     |            ✅ Ideal            |
| **Classes requiring Inheritance hierarchies**                     | ❌ Cannot extend classes |            ✅ Ideal            |

---

## 6. Lombok vs Pure Java Records in Modern LLD

In interviews, writing out `@Getter`, `@Setter`, `@AllArgsConstructor` from Project Lombok is acceptable only if agreed upon with the interviewer. However, using native **Java Records** is universally preferred because it is built into the language standard, requires no third-party compiler plugins, and guarantees immutability at the JVM bytecode level.

---

## 7. Interview Q&A

**Q: Can records have non-static mutable fields?**
*Answer:* No. All instance fields of a record are implicitly `final`. If a record holds a reference to a mutable object (like a `List`), the reference itself cannot change, but callers could theoretically mutate the list elements if a defensive unmodifiable copy is not made in the compact constructor.
