## OOP Fundamentals (Q1–Q8)

**Q1. What is the difference between a class and an object?**
Answer: A class is a blueprint or template that defines the attributes (state) and methods (behavior) that its instances will have — it does not itself occupy memory for instance data. An object is a concrete instance of a class created at runtime, with its own copy of instance attributes (unless declared as class-level/shared attributes) but sharing the class's method definitions. For example, `class Car` defines that every car has a `speed` and a `drive()` method; `my_car = Car()` is one specific object with its own `speed` value.

**Q2. Explain the four pillars of OOP with a concrete example each.**
Answer: Encapsulation bundles data and behavior together and restricts direct access (e.g. a `BankAccount` class exposes `deposit()`/`withdraw()` but keeps `_balance` private, so balance can't be corrupted by direct assignment). Abstraction hides implementation details behind a simple interface (a `PaymentGateway` abstract class exposes `pay(amount)` without callers knowing whether it hits Stripe or PayPal internally). Inheritance lets a class reuse and extend another's behavior (`SavingsAccount(Account)` inherits deposit/withdraw and adds interest calculation). Polymorphism lets different objects respond to the same call differently (`account.calculate_interest()` behaves differently for `SavingsAccount` vs `CheckingAccount`).

**Q3. What is the difference between method overriding and method overloading, and does Python support both?**
Answer: Overriding is when a subclass redefines a method that already exists in its parent class with the same signature, changing behavior at runtime via dynamic dispatch — Python fully supports this natively. Overloading is having multiple methods with the same name but different parameter signatures, resolved at compile time in languages like Java/C++. Python does not support true overloading because it only keeps the last-defined method with a given name; instead, Python developers simulate overloading using default arguments, `*args`/`**kwargs`, type checking inside a single method, or the `functools.singledispatch` decorator for type-based dispatch.

**Q4. Composition vs inheritance — when would you choose one over the other?**
Answer: Inheritance models an "is-a" relationship and is appropriate when subclasses are genuinely specialized versions of the base class that should inherit its entire contract (a `Square` is-a `Shape`). Composition models a "has-a" relationship, where an object is built by holding references to other objects that provide functionality (a `Car` has-an `Engine`). Composition is generally preferred in LLD interviews because it is more flexible — behavior can be swapped at runtime by injecting a different collaborator (e.g. swapping engine types), it avoids the fragile base class problem, and it avoids deep, hard-to-reason-about inheritance chains. The guiding heuristic is "favor composition over inheritance."

**Q5. What is the difference between `@staticmethod` and `@classmethod` in Python?**
Answer: A `@staticmethod` does not receive an implicit first argument (`self` or `cls`) — it behaves like a plain function that is simply namespaced under the class because it's logically related, and it cannot access or modify class/instance state. A `@classmethod` receives `cls` as its first argument (the class itself, not an instance) and is commonly used for alternate constructors (e.g. `Date.from_string("2024-01-01")`) or for methods that need to create/return an instance of the class, including of a subclass if called on one. Choose `classmethod` when the method needs to know or construct the class; choose `staticmethod` for a pure utility function that just happens to live in the class's namespace.

**Q6. What are Python magic (dunder) methods and why do they matter in LLD?**
Answer: Magic methods are special methods surrounded by double underscores (`__init__`, `__eq__`, `__repr__`, `__str__`, `__len__`, `__iter__`, `__lt__`, `__enter__`/`__exit__`, `__hash__`) that Python's interpreter calls implicitly to implement built-in behaviors like construction, string representation, equality, iteration, comparison, and context management. In LLD they matter because idiomatic Python solutions use them instead of Java-style getter/setter boilerplate — e.g. implementing `__lt__` lets your custom `Task` objects be sorted directly with `sorted()` or placed in a `heapq` for a priority-queue-based scheduler, and implementing `__eq__`/`__hash__` lets custom objects be used correctly as dict keys or in sets.

**Q7. What are Python dataclasses and when should you use them in an LLD interview?**
Answer: `@dataclass` (from the `dataclasses` module) is a decorator that automatically generates `__init__`, `__repr__`, and `__eq__` (and optionally `__lt__` etc. via `order=True`) based on type-annotated class attributes, eliminating repetitive boilerplate. They're ideal for simple value/data-holder objects in an LLD design — e.g. a `Point`, `Money`, or `Seat` class that primarily carries data with little behavior. You should avoid dataclasses for classes with rich behavior, invariants that need enforcement in `__init__`, or where you want to hide implementation details, since dataclass fields are public by default and immutability requires the extra `frozen=True` flag.

**Q8. What does it mean for an object to be "immutable," and why does it matter in system design?**
Answer: An immutable object's state cannot be changed after construction — any "modification" produces a new object instead (e.g. Python strings, tuples, or a `frozen=True` dataclass). Immutability matters in LLD because it eliminates a whole class of bugs around shared mutable state, makes objects inherently thread-safe without locks, allows safe use as dict keys/set members, and enables patterns like the Value Object pattern (e.g. `Money`, `Coordinates`) where equality is based on value not identity. In multi-threaded systems (e.g. a booking or ticketing system with concurrent requests) immutable value objects reduce race-condition surface area significantly compared to mutable shared state.

## SOLID Principles (Q9–Q14)

**Q9. Explain the Single Responsibility Principle with an LLD example of a violation and its fix.**
Answer: SRP states a class should have only one reason to change. A violation: a `Report` class that both computes report data AND formats it as HTML AND saves it to a file — a change to the file format, the HTML template, or the storage medium all force edits to the same class. The fix is to split responsibilities into `ReportGenerator` (computes data), `ReportFormatter` (formats as HTML/PDF/etc.), and `ReportRepository` (handles persistence), each with one reason to change and independently testable/replaceable.

**Q10. How does the Open/Closed Principle relate to the Strategy and Factory patterns?**
Answer: OCP says software entities should be open for extension but closed for modification. The classic violation is a method with a growing `if/elif` chain that must be edited every time a new case is added. The Strategy pattern satisfies OCP for *behavior* — new algorithms are added as new classes implementing a common interface, without touching the code that uses the strategy. The Factory Method pattern satisfies OCP for *object creation* — new types are added as new factory branches/registrations without modifying the client code that requests objects from the factory. Both let you extend the system by adding new classes rather than modifying tested existing code.

**Q11. What does the Liskov Substitution Principle actually require, and what is the classic Rectangle/Square counterexample?**
Answer: LSP requires that objects of a subclass must be substitutable for objects of the base class without altering the correctness of the program — the subclass must honor the base class's behavioral contract (pre-conditions can't be strengthened, post-conditions can't be weakened). The classic counterexample: `Square` extends `Rectangle` and overrides `set_width`/`set_height` to keep both sides equal. Code that relies on `Rectangle`'s contract (setting width independently of height) breaks when handed a `Square`, because setting width unexpectedly also changes height. This shows that "is-a" in the real world (a square is a rectangle mathematically) doesn't always translate to a valid "is-a" in a type hierarchy if behavior/contracts diverge.

**Q12. Give a real LLD example of violating the Interface Segregation Principle and how you'd fix it.**
Answer: Suppose a `Worker` interface has `work()`, `eat()`, and `sleep()` methods, and a `RobotWorker` class must implement it — but robots don't eat or sleep, so those methods end up as empty stubs or raise `NotImplementedError`, which is an ISP violation (a class is forced to depend on methods it doesn't use). The fix is to segregate into smaller, role-specific interfaces: `Workable`, `Eatable`, `Sleepable`, and have `HumanWorker` implement all three while `RobotWorker` implements only `Workable`. This keeps each interface focused and clients only depend on what they actually need.

**Q13. Explain Dependency Inversion Principle and show how dependency injection implements it.**
Answer: DIP states that high-level modules should not depend on low-level modules directly — both should depend on abstractions, and abstractions should not depend on details. In practice: a `NotificationService` (high-level) should not instantiate `EmailSender` (low-level, concrete) directly inside itself; instead it should depend on an abstract `MessageSender` interface, and the concrete `EmailSender` or `SMSSender` implementation is passed in ("injected") via the constructor: `NotificationService(sender: MessageSender)`. This inversion means the high-level policy code doesn't need to change when you swap or add new low-level implementations, and it makes the class trivially testable by injecting a mock/fake sender.

**Q14. In a real interview, how would you demonstrate applying all 5 SOLID principles to a single small design (e.g. a notification system)?**
Answer: Start with a `Notification` abstract base defining `send(message)` (supports OCP/DIP by being an abstraction other classes depend on). Create separate concrete senders — `EmailNotification`, `SMSNotification`, `PushNotification` — each with the single responsibility of sending via one channel (SRP). Adding a new channel means adding a new class, not modifying existing ones (OCP). Any concrete sender must be fully substitutable wherever `Notification` is expected, honoring the same contract (LSP). If some channels support delivery receipts and others don't, split into `Notification` and an optional `TrackableNotification` interface rather than forcing all senders to implement a `get_delivery_receipt()` they can't support (ISP). Finally, a `NotificationManager` depends only on the abstract `Notification` type and receives concrete senders via constructor injection, never instantiating them itself (DIP).

## UML & Object Modeling (Q15–Q18)

**Q15. What is the difference between aggregation and composition, and how do you express each in Python code?**
Answer: Both represent "has-a" relationships (whole/part), but they differ in lifecycle ownership. Aggregation is a weak "has-a" — the part can exist independently of the whole and can be shared across multiple wholes (a `Team` has `Player`s, but players exist and are created before/independently of any team, and can move teams); in Python this looks like objects being created externally and passed into a constructor or setter: `def __init__(self, players): self.players = players`. Composition is a strong "has-a" — the part's lifecycle is bound to the whole; when the whole is destroyed, so is the part (a `Car` owns its `Engine`; you never share one `Engine` instance between two `Car`s); in Python this looks like the container creating the part itself inside its own constructor: `def __init__(self): self.engine = Engine()`.

**Q16. How do you represent multiplicity and relationships when translating a UML class diagram into Python classes?**
Answer: Multiplicity (1, 0..1, 0..*, 1..*) tells you what data structure to use for a reference. A 1-to-1 relationship becomes a single attribute reference (`self.engine: Engine`). A 1-to-many becomes a collection attribute, typically a `list` or `dict` keyed by ID for fast lookup (`self.orders: list[Order]` or `self.orders_by_id: dict[str, Order]`). Optional (0..1) relationships are typed as `Optional[X]` and initialized to `None`. Many-to-many relationships usually require an explicit association/join class if the relationship itself carries data (e.g. `Enrollment` between `Student` and `Course` carrying a grade), mirroring how you'd model a join table in a relational schema.

**Q17. What is the difference between an "association" and a "dependency" in UML, and does it matter for LLD interviews?**
Answer: An association is a structural, usually long-lived relationship where one class holds a reference to another as an attribute (e.g. `Order` holds a `Customer` reference for its whole lifetime). A dependency is a weaker, more transient relationship where one class merely uses another momentarily — e.g. as a parameter or local variable inside a single method — without storing a reference (e.g. a `Order.apply_discount(discount: DiscountPolicy)` method that takes a policy object just for that call). It matters in interviews because correctly distinguishing them communicates that you understand object lifetimes and coupling — over-storing references you don't need increases coupling and memory retention unnecessarily.

**Q18. Walk through how you'd draw (verbally describe) a UML class diagram for a simple Library system with Book, Member, and Loan.**
Answer: `Book` has attributes like `isbn`, `title`, `author`, and a status; `Member` has `member_id`, `name`, and a list of active loans. `Loan` is an association class connecting `Book` and `Member` because the relationship itself carries data — `loan_date`, `due_date`, `returned_date` — that doesn't belong to either `Book` or `Member` alone. The relationship between `Library` and `Book` is composition (books are owned/managed by the library catalog and don't exist independently in this domain), while the relationship between `Member` and `Loan` is aggregation (loans reference members but a member's identity doesn't depend on having loans). This kind of walkthrough demonstrates you can identify when a relationship needs its own class versus being a plain reference.

## Design Patterns (Q19–Q33)

**Q19. What is the difference between Factory Method and Abstract Factory?**
Answer: Factory Method is about a single creation method (often in a base/creator class or as a standalone function) that returns one product type, with subclasses or branches deciding which concrete class to instantiate — it solves "which one class do I create?" Abstract Factory is about creating *families* of related products that must be used together, exposing multiple creation methods on one factory interface (e.g. `create_button()` and `create_checkbox()`) so that swapping the whole factory implementation swaps an entire consistent family (e.g. all Dark-theme widgets vs all Light-theme widgets). A useful mental model: Abstract Factory is often implemented using multiple Factory Methods internally, one per product type in the family.

**Q20. Compare Strategy and State patterns — they look structurally identical, so what's the real difference?**
Answer: Structurally, both involve a context holding a reference to an interchangeable object implementing a common interface — that's why they're often confused. The difference is intent and control of transitions: in Strategy, the client explicitly chooses and sets the algorithm from outside (e.g. `cart.set_payment_strategy(CreditCardPayment())`), and strategies typically don't know about each other or trigger transitions. In State, the state objects themselves are usually responsible for transitioning the context to the next state (e.g. `IdleState.handle()` sets `context.state = RunningState()`), and the context's behavior appears to change automatically as its internal state evolves, driven by the state objects, not by external client calls.

**Q21. Compare Adapter and Facade — both "wrap" other classes, so when do you use which?**
Answer: Adapter's intent is compatibility — it converts one specific interface into another interface a client already expects, typically wrapping a single class (often third-party/legacy) with a one-to-one method translation (e.g. wrapping `OldPrinter.print_old()` to expose a `print()` method matching your app's `Printer` interface). Facade's intent is simplification — it wraps and coordinates *multiple* subsystem classes behind one simplified high-level interface, reducing the number of objects/calls a client needs to know about (e.g. `ComputerFacade.start()` internally calls `cpu.freeze()`, `memory.load()`, `cpu.execute()`). Use Adapter when you need to make an incompatible interface fit; use Facade when you want to hide complexity, not incompatibility.

**Q22. Compare Proxy and Decorator — both wrap an object with the same interface, so what distinguishes them?**
Answer: Both implement the same interface as the object they wrap and delegate calls to it, but their intent differs. Proxy controls *access* to the wrapped object — common uses are lazy initialization (don't create the expensive real object until needed), access control/permission checks, caching, or representing a remote object — and typically wraps exactly one specific real subject, often instantiating or managing it internally. Decorator adds *additional behavior/responsibility* to the wrapped object dynamically and is designed to be stacked — you can wrap a decorator around another decorator around the real object (e.g. `LoggingDecorator(CachingDecorator(RealService()))`) to compose multiple independent behaviors, whereas proxies are usually not chained this way.

**Q23. How would you implement the Observer pattern in Python for a stock price alert system?**
Answer: Define a `Subject` (the stock) that maintains a list of `Observer` objects and exposes `attach(observer)`, `detach(observer)`, and `notify()`, calling `observer.update(self)` on each registered observer whenever price changes. Define an `Observer` interface with an `update(subject)` method. Concrete observers like `EmailAlertObserver` or `SMSAlertObserver` implement `update()` to check if the new price crosses a threshold and, if so, send an alert. The `Stock` class calls `self.notify()` inside its `set_price()` method after updating `self._price`, decoupling the stock from knowing exactly who's watching it or how they respond — you can add new alert channels without changing `Stock` at all.

**Q24. Design the Command pattern for a smart home remote control with undo support.**
Answer: Define a `Command` interface with `execute()` and `undo()` methods. Concrete commands like `LightOnCommand` wrap a `Light` receiver and implement `execute()` as `light.turn_on()` and `undo()` as `light.turn_off()`. The `RemoteControl` (invoker) holds a mapping of buttons to `Command` objects and, when a button is pressed, calls `command.execute()` while pushing the command onto a history stack. Pressing "undo" pops the last command from the stack and calls its `undo()`. This decouples the remote (invoker) from the light (receiver) entirely — the remote doesn't need to know what turning a light on actually does, and new devices/commands can be added without changing the remote's code.

**Q25. Explain the Template Method pattern with an example of processing different file formats (CSV, JSON, XML).**
Answer: Define an abstract `DataProcessor` base class with a concrete `process()` method that calls, in fixed order, `self.read()`, `self.parse()`, `self.transform()`, `self.write()` — this is the algorithm skeleton and it's marked as final/non-overridden. Each step is declared as an `@abstractmethod` that concrete subclasses like `CSVProcessor`, `JSONProcessor`, and `XMLProcessor` must implement with format-specific logic, while `transform()` might have a shared default implementation reusable across all formats (a "hook" that subclasses can optionally override). This ensures the overall workflow order is enforced once in the base class and can't be accidentally changed or reordered by subclasses, while still allowing per-format customization of individual steps.

**Q26. When would you use the Chain of Responsibility pattern instead of a simple if/elif chain?**
Answer: Chain of Responsibility is preferable when you want to decouple the sender of a request from its receivers and allow multiple potential handlers, determined dynamically at runtime, without the sender knowing which one will actually handle it or how many there are. A concrete example is a support-ticket escalation system: `Level1Handler -> Level2Handler -> ManagerHandler`, where each handler checks if it can resolve the ticket and, if not, passes it to `self.next.handle(ticket)`. Unlike a hardcoded if/elif chain, handlers can be added, removed, or reordered at runtime by just relinking the chain, and each handler is independently testable and only knows about the "next" link, not the whole chain's structure.

**Q27. How would you use the Composite pattern to model a file system (files and folders)?**
Answer: Define a common interface, e.g. `FileSystemComponent`, with a method like `get_size()`. `File` is a leaf that implements `get_size()` by returning its own byte size. `Folder` is a composite that holds a list of child `FileSystemComponent` objects (which can themselves be files or other folders) and implements `get_size()` by recursively summing `child.get_size()` over all children. This lets client code call `.get_size()` uniformly on either a single file or an entire nested folder tree without needing to check "is this a file or a folder" anywhere — the recursion handles arbitrary nesting depth transparently.

**Q28. Explain how the Builder pattern solves the "telescoping constructor" problem, with an example.**
Answer: A telescoping constructor problem arises when a class has many optional parameters, leading to constructors like `Pizza(size, cheese=True, olives=False, mushrooms=False, extra_cheese=False, ...)` that become unreadable and error-prone (easy to mix up positional boolean args). The Builder pattern instead exposes a fluent, chainable API: `PizzaBuilder().set_size("large").add_cheese().add_olives().build()`, where each method returns `self` and sets one aspect of the object being constructed, and `build()` returns the finished, often validated, object at the end. This makes construction self-documenting (each option is named at the call site), allows optional parameters to be omitted entirely, and lets you enforce invariants/validation in `build()` before returning the object.

**Q29. What thread-safety issue exists in a naive Python Singleton implementation, and how do you fix it?**
Answer: A naive Singleton using `__new__` with a check like `if cls._instance is None: cls._instance = super().__new__(cls)` has a race condition under multi-threading: two threads could both pass the `is None` check simultaneously before either sets `_instance`, resulting in two separate instances being created. The standard fix is to guard the instance-creation block with a `threading.Lock` (double-checked locking): check if the instance is `None`, acquire the lock, check again inside the lock, and only then create the instance — the second check inside the lock prevents redundant creation if another thread already initialized it while this thread was waiting for the lock.

**Q30. What is the Prototype pattern and how does Python's `copy` module support it?**
Answer: Prototype pattern creates new objects by cloning an existing "prototype" instance rather than instantiating from scratch, which is useful when object construction is expensive (e.g. loads data from a database or file) or when you want a new object that's "mostly the same" with small tweaks. Python's built-in `copy` module supports this directly: `copy.copy(obj)` performs a shallow copy (nested mutable objects are still shared by reference), while `copy.deepcopy(obj)` recursively copies nested objects too, so mutating the clone's nested state doesn't affect the original. Classes can customize deep-copy behavior by implementing `__deepcopy__(self, memo)`.

**Q31. How would you design a plugin/extension system using patterns, avoiding modification of core code for each new plugin?**
Answer: Define an abstract `Plugin` interface with a standard method like `run(context)`. Core application code depends only on this abstraction (satisfying DIP) and discovers/loads concrete plugins via a registry or Factory (e.g. a dict mapping plugin names to classes, populated via a `@register_plugin("name")` decorator) rather than hardcoding imports. This combines Factory Method (to instantiate the right plugin by name/config without an if/elif chain) with OCP (adding a new plugin means writing a new class and registering it, never touching the core dispatch logic) and often Strategy (the core swaps which plugin/algorithm runs based on configuration).

**Q32. Difference between Memento and Command when both are used for "undo" — why might you need both together?**
Answer: Command encapsulates an *action* (what operation was requested) as an object with `execute()`/`undo()` — undoing via Command means executing the *inverse operation* (e.g. `undo()` of `AddTextCommand` deletes the text that was added), which requires the command to know how to reverse its own effect. Memento instead captures a *snapshot of state* at a point in time, without needing to know how to compute an inverse operation — undo means simply restoring the saved snapshot. They're often combined when the inverse of an operation is hard or impossible to compute algorithmically (e.g. a complex image filter): the Command's `execute()` first asks the receiver to create a `Memento` of its current state before making the change, and `undo()` just restores that memento, rather than trying to mathematically reverse the filter.

**Q33. How does the Mediator pattern reduce coupling in a chat room or air-traffic-control-style system, compared to objects communicating directly?**
Answer: Without a mediator, every participant object (e.g. each `User` in a chat room) would need direct references to every other participant to send them messages, creating an O(n²) web of dependencies that's hard to maintain and test. With Mediator, all participants hold a reference only to a central `Mediator` (e.g. `ChatRoom`) and communicate exclusively through it — `user.send(message)` calls `self.mediator.broadcast(self, message)`, and the mediator is solely responsible for routing the message to the appropriate other participants. This centralizes and encapsulates the interaction logic in one place, so participants don't need to know about each other at all, and communication rules (e.g. muting, routing to specific rooms) can be changed by editing only the mediator.

## Python-Specific LLD Features (Q34–Q37)

**Q34. How would you enforce that a class cannot be instantiated directly and must be subclassed, in Python?**
Answer: Use the `abc` module — inherit from `abc.ABC` and decorate at least one method with `@abstractmethod`. Attempting to instantiate the class directly (`MyAbstractClass()`) raises a `TypeError` at runtime because Python checks whether all abstract methods have been overridden before allowing instantiation. This is the idiomatic way to define interfaces/abstract base classes in Python for LLD designs (e.g. a `PaymentStrategy(ABC)` with `@abstractmethod def pay(self, amount): ...`), and it also documents the contract subclasses must fulfill, similar to interfaces in Java.

**Q35. What is `functools.singledispatch` and how can it help simulate method overloading in LLD designs?**
Answer: `functools.singledispatch` is a decorator that lets you register different implementations of a function based on the type of its first argument, giving type-based dispatch similar to overloading. You define a generic base function decorated with `@singledispatch`, then register type-specific implementations with `@my_func.register(SomeType)`. This is useful in LLD when, for example, a `render()` function needs fundamentally different logic for a `Circle` vs a `Square` vs a `Triangle` argument but you don't want to (or can't) add the logic as a method on each shape class — commonly used to keep rendering/serialization logic separate from the domain model classes (avoiding polluting simple data classes with format-specific code).

**Q36. Why are Python's context managers (`__enter__`/`__exit__`, `with` statement) relevant to LLD interview designs?**
Answer: Context managers guarantee that setup and teardown code run reliably, including on exceptions, which matters whenever a design involves acquiring and releasing a resource — e.g. a `with lock:` around a critical section in a concurrent booking system, a `with db.transaction():` block that commits on success and rolls back on exception, or a `with ResourcePool.acquire() as resource:` pattern in a connection-pool design. Demonstrating you'd model such resource lifecycles with `__enter__`/`__exit__` (or `contextlib.contextmanager`) rather than manual try/finally boilerplate shows idiomatic Python and correct handling of the RAII-style "acquire/release" pattern that interviewers often probe for in systems like parking lots (acquiring/releasing a spot) or elevators (acquiring/releasing a request slot).

**Q37. How do Python's `Enum` classes improve on using plain strings or integers for a status field (e.g. order status)?**
Answer: Using raw strings like `"PENDING"` or ints like `1` for a status field is error-prone — typos aren't caught until runtime, there's no IDE autocomplete, and there's no single source of truth for valid values. `class OrderStatus(Enum): PENDING = "pending"; CONFIRMED = "confirmed"; CANCELLED = "cancelled"` centralizes all valid values, gives autocomplete/type-checking support, prevents invalid values from being assigned by convention, and comparisons (`status == OrderStatus.PENDING`) are explicit and safe. Enums are used pervasively across LLD problems for state fields — order status, parking spot type, seat status, elevator direction — and are frequently the backing type for a State-pattern's discriminator or a Strategy-pattern's lookup key.

## System Design Walkthroughs (Q38–Q50)

**Q38. How would you prevent double-booking of the same movie seat in a Movie Booking system?**
Answer: Model each `Seat` with a status enum (`AVAILABLE`, `LOCKED`, `BOOKED`) and require that reserving a seat go through an atomic "check-and-set" operation rather than a separate read-then-write, since a read-then-write allows a race condition where two threads both see `AVAILABLE` before either writes `BOOKED`. In a single-process design, protect the seat's state transition with a lock (`threading.Lock` per seat or per show) so the check-and-transition is atomic. Additionally introduce a short-lived "lock/hold" state (e.g. 5-10 minutes) when a user starts checkout, using a scheduled expiry (timer or background sweep) to release seats abandoned mid-checkout back to `AVAILABLE`, and only transition `LOCKED -> BOOKED` upon confirmed payment. In a distributed/DB-backed version, this maps to a DB-level optimistic lock (version column) or a `SELECT ... FOR UPDATE` / conditional update (`UPDATE seats SET status='BOOKED' WHERE id=? AND status='AVAILABLE'`), succeeding only if the row hasn't changed underneath you.

**Q39. Design the class structure for a Parking Lot system — what are the key classes and relationships?**
Answer: Core classes: `ParkingLot` (top-level, composition of multiple `ParkingFloor`s), `ParkingFloor` (composition of multiple `ParkingSpot`s), `ParkingSpot` (abstract or with a `SpotType` enum — motorcycle/compact/large — and a status), `Vehicle` (abstract base with subclasses `Motorcycle`, `Car`, `Truck`, each declaring which spot types fit it), `Ticket` (association between a `Vehicle` and the `ParkingSpot`/entry time it occupies), and a `ParkingRateStrategy` (Strategy pattern) to compute fees differently per vehicle type or duration tiers. Spot assignment logic (finding the nearest/smallest suitable free spot for a vehicle type) is a good candidate for the Strategy pattern too, so you can swap "nearest-first" vs "best-fit" allocation algorithms. A `Singleton` is sometimes used for the top-level `ParkingLot` manager if the design assumes exactly one lot instance per process.

**Q40. How would you design the debt-simplification algorithm in a Splitwise-like expense-splitting system?**
Answer: Model each user's net balance across the whole group as a single signed number (positive = is owed money, negative = owes money), computed by summing all their individual pairwise balances from every expense they participated in. The simplification algorithm then repeatedly picks the user with the maximum positive balance (biggest creditor) and the user with the maximum negative balance (biggest debtor, i.e. minimum balance), settles the smaller of the two absolute amounts between them (creating one settlement transaction), reduces both balances by that amount, and repeats until all balances are zero (or within a rounding epsilon) — this is a greedy algorithm, efficiently implementable with two max-heaps (one for creditors, one for debtors), running in O(n log n) and guaranteed to produce at most n-1 transactions for n users with nonzero balances. This decouples "who owes what to whom individually" (per-expense split records) from "the minimum set of transactions to settle up" (the simplified graph), which should be two separate methods/classes in the design.

**Q41. What object model and matching algorithm would you use for a Cab Booking (like Uber/Ola) system's driver-matching?**
Answer: Core classes: `Rider`, `Driver` (with a live `Location` and an availability status enum), `Trip` (association between a matched `Rider` and `Driver`, tracking status: `REQUESTED -> MATCHED -> IN_PROGRESS -> COMPLETED`), and a `MatchingStrategy` (Strategy pattern) so different matching algorithms can be swapped — e.g. "nearest available driver" using a simple distance calculation, versus a more advanced geo-hashing/quad-tree spatial index for city-scale driver lookup that avoids scanning every driver. The matching flow: when a `Trip` is requested, query the spatial index for available drivers within an expanding radius, rank candidates by the chosen strategy (distance, ETA, rating), attempt to reserve the top candidate atomically (to avoid two riders being matched to the same driver — same double-booking concern as Q38, solved with a per-driver status lock/conditional update), and fall back to the next candidate if reservation fails.

**Q42. How would you model an ATM system's states, and what pattern fits best?**
Answer: The State pattern fits naturally because an ATM's behavior for the same physical button presses changes completely depending on its current stage. Model states as classes implementing a common `ATMState` interface with methods like `insert_card()`, `enter_pin()`, `select_transaction()`, `dispense_cash()`, `eject_card()` — concrete states include `IdleState`, `HasCardState`, `PinEnteredState`, `TransactionSelectedState`, `DispensingCashState`. Each state only implements the operations valid in that state (others might raise an error or no-op) and, on success, transitions the `ATMContext` to the next state (e.g. `HasCardState.enter_pin(correct_pin)` transitions to `PinEnteredState` or back to `IdleState` after repeated failures, e.g. capturing the card). This keeps the ATM's core class free of a giant conditional and localizes each state's valid operations and transitions into its own class, making it easy to add new states (e.g. `LanguageSelectionState`) without touching existing ones.

**Q43. Design a Vending Machine — what state machine and inventory model would you use?**
Answer: Similar to the ATM, use the State pattern with states like `IdleState`, `HasMoneyState`, `DispensingState`, `OutOfStockState`, each implementing `insert_coin()`, `select_product()`, `dispense()`, `cancel()` appropriately for that stage — e.g. `select_product()` is a no-op/error in `IdleState` (no money inserted yet) but triggers dispensing logic in `HasMoneyState` if sufficient funds and stock exist. For inventory, model `Slot` objects each holding a `Product` reference, a `price`, and a `quantity` count, keyed by a slot code (e.g. "A3") in a `dict[str, Slot]` on the `VendingMachine`, so lookups and stock decrements are O(1). Change/refund calculation (returning the correct combination of coins) is a good candidate for a small dedicated `ChangeCalculator` (greedy coin algorithm), kept separate from the state machine so it's independently testable.

**Q44. How would you design an Elevator system's request-scheduling algorithm?**
Answer: Core classes: `Elevator` (tracks current floor, direction enum `UP`/`DOWN`/`IDLE`, and two priority queues/sorted sets — one for pending up-requests above current floor, one for pending down-requests below), `ElevatorRequest` (floor + desired direction), and an `ElevatorController`/`Dispatcher` that owns multiple `Elevator`s and decides which elevator services an incoming hall-call request (typically the one that can reach the requesting floor soonest, considering current direction and load — this dispatch decision is a good Strategy pattern candidate to allow swapping "nearest elevator" vs "least busy" algorithms). The core movement algorithm is the classic SCAN/LOOK disk-scheduling algorithm: an elevator continues in its current direction servicing all requests along the way, then reverses only once there are no more requests further in that direction — this avoids starvation and minimizes unnecessary direction changes compared to naive FIFO servicing.

**Q45. What's the object model for a Library Management system, and how do you handle book reservations/holds?**
Answer: Core classes: `Book` (catalog metadata) and separate `BookCopy` (a physical copy with its own status: `AVAILABLE`, `LOANED`, `RESERVED`, `LOST`) since a library owns multiple physical copies of the same title; `Member` with borrowing limits and a fine balance; `Loan` (association class linking a `Member` and a `BookCopy` with due dates); and `Reservation`/`Hold` (a queue per `Book` title of members waiting for the next available copy, typically a FIFO queue per title). When a `BookCopy` is returned, the system checks that title's hold queue: if non-empty, the copy transitions to `RESERVED` and is offered to the next member in line (with an expiry window) rather than becoming generally `AVAILABLE`; if the queue is empty, it becomes `AVAILABLE` for anyone. Overdue fine calculation is naturally a Strategy (flat-rate vs tiered-rate per day) to allow different policies per member type or book category.

**Q46. How would you design a URL Shortener's core encoding logic and handle collisions?**
Answer: The core design decision is how to generate the short code. A counter-based approach maintains a global (or sharded, for scale) auto-incrementing integer ID per new URL and encodes that ID into a base-62 string (`[a-zA-Z0-9]`) — this guarantees no collisions by construction since IDs are unique, and base-62 keeps short codes compact (a 62^6 space covers ~56 billion URLs in 6 characters). An alternative hash-based approach computes a hash (e.g. MD5) of the long URL and takes the first N characters, which requires an explicit collision check (look up if that code is already taken by a *different* long URL) and a retry/salt strategy on collision — more complex than counter-based but avoids needing a centralized counter service. Class-wise: `URLShortenerService` (facade exposing `shorten(url)`/`resolve(code)`), an injected `IDGenerator` or `HashGenerator` (Strategy, so you can swap encoding schemes), and a `URLRepository` (abstraction over storage — e.g. a key-value store) mapping short code to long URL plus metadata (creation time, expiry, click count).

**Q47. How would you model group messaging and message delivery status in a WhatsApp-like system?**
Answer: Core classes: `User`, `Chat` (abstract base with `PrivateChat` and `GroupChat` subclasses — GroupChat additionally holds a list of `User` members and an admin set), `Message` (sender, content, timestamp, and a per-recipient delivery-status map since in a group each member has independent `SENT`/`DELIVERED`/`READ` status rather than one global status), and an `Observer`-pattern-based notification flow where each `User`'s connected client(s) subscribe to their `Chat`s so new messages are pushed in real time rather than polled. Group membership changes (`add_member`, `remove_member`, `promote_admin`) are naturally modeled as `Command` objects if you want an audit/history log of group admin actions. Message delivery-status transitions (`SENT -> DELIVERED -> READ`) are best modeled as an ordered enum with a rule that status can only move forward, never backward, per recipient.

**Q48. Design the playlist and playback object model for a Spotify-like music system, and where would you apply the Strategy pattern?**
Answer: Core classes: `Song` (metadata: title, artist, duration), `Playlist` (composition — an ordered collection of `Song` references, owned by a `User`), and a `Player` that holds the current playlist and current index. The Strategy pattern fits playback order: define a `PlaybackStrategy` interface with a `next()` method, with concrete strategies `SequentialPlayback` (index + 1), `ShufflePlayback` (random unplayed index, tracking a "already played" set to avoid repeats until exhausted), and `RepeatOnePlayback` (always returns the same index) — the `Player` holds a reference to the current strategy and swapping "shuffle on/off" is just swapping which strategy object it delegates `next()` to, with zero changes to `Player`'s own code. Recommendation/"related songs" logic is typically kept as a separate injected service/strategy as well, so it can evolve (rule-based vs ML-based) independently of the core playback model.

**Q49. How would you design the shopping cart and pricing/discount logic for an Amazon-like cart system?**
Answer: Core classes: `Product` (catalog item with base price and stock), `CartItem` (association of a `Product` and a quantity), `Cart` (composition — owned list of `CartItem`s, belongs to one `User`), and a chain/list of `DiscountStrategy` (or `PricingRule`) objects applied in sequence to compute the final total — e.g. `PercentageDiscount`, `FlatAmountDiscount`, `BuyOneGetOneDiscount`, `CouponCodeDiscount` — each implementing a common `apply(cart) -> discount_amount` interface, letting the checkout process stack multiple promotions without hardcoding their combination logic (good Strategy or even Chain-of-Responsibility candidate if discounts must be applied in a specific priority order with some being mutually exclusive). Stock reservation when items are added to cart (to avoid overselling during checkout) follows the same "atomic check-and-set" concern as Q38's seat-locking, typically with a short-lived hold on inventory quantity that expires if checkout isn't completed.

**Q50. What is the standard 7-step process you should follow when presenting any LLD problem in a live interview?**
Answer: (1) Clarify requirements and scope — ask about scale, must-have vs nice-to-have features, and constraints before writing any code, to avoid designing the wrong thing. (2) Identify the core entities/nouns in the problem and their attributes (e.g. for Parking Lot: Vehicle, Spot, Floor, Ticket). (3) Identify relationships between entities (association/aggregation/composition/inheritance) and sketch this verbally or as a rough UML class diagram. (4) Define the key interfaces/abstract classes first, since this establishes contracts before implementation details. (5) Identify which design patterns naturally fit the problem's varying behaviors, object creation needs, or structural composition (don't force-fit patterns that aren't needed — over-engineering is a common interview red flag). (6) Write the actual Python class skeletons with method signatures, key attributes, and enough implementation to show the design works, prioritizing breadth (getting the whole system sketched) over exhaustively implementing every method. (7) Discuss extensibility, edge cases, and trade-offs explicitly (e.g. "if we needed to support X in the future, this design accommodates it by Y") — this final step is where many candidates who "answer correctly" fail to stand out, because interviewers weight the ability to reason about trade-offs as highly as the initial design itself.
